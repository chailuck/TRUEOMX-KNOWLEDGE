Request_KNOX_LOCK_DEVICE

TIBCO BusinessEvents FM — Samsung Knox Device Lock (per-offer iteration, 3-level loop)
Rule: Rules.OMConsumers.OMXFM.Request.Request_KNOX_LOCK_DEVICE Priority: 5 forwardChain: true Author: DESKTOP-995HR2V Backend: Samsung Knox Proxy Service Generated: 2026-09-16
§1 — Overview & Purpose

Fires when ActivityID == "KNOX_LOCK_DEVICE". This FM is unique: it iterates per offer rather than per subscriber. For each qualifying subscriber offer (SubscriberOffers), it sends a KNOX_PROXY_SERVICE lockDevice request to Samsung Knox. This allows locking devices associated with individual offers on a subscriber's account during full suspension.

3-Level nesting: ParentOU → Subscriber → SubscriberOffers. RefId is subRefId:offer.Soc:filter where filter is the FE_OR_CCBS ExtendedInfo value on that offer.

TEL required: Parameter TEL must be present in activity parameters. If missing → throws DATA_ISSUE exception.

Notification message: Resolved via DecisionTables.KnoxNotifyMsgVRF(orderType, "LOCK", activityReason, lang, msg) decision table lookup.

§5 — Execution Flow
  1. Load TEL from GetActivityParameterValueFromKey("TEL", params) — throws DATA_ISSUE if null
  2. Outer loop: ParentOU[i]
  3.   Middle loop: Subscriber[j] in POU
  4.     Compute subRefId = Subscriber[j].RefId
  5.     Apply subscriber-level PreExecCheck
  6.     Inner loop: SubscriberOffers[k]
  7.       Compute filter = FE_OR_CCBS ExtendedInfo value
  8.       Compute refId = subRefId + ":" + offer.Soc + ":" + filter
  9.       Skip if existing completed response found
  10.       Lookup notification message via KnoxNotifyMsgVRF decision table
  11.       Fire KNOX_PROXY_SERVICE event: lockDevice with IMEI_KNOX, tel, message
  12.       Increment RequestCount; ActionRequestEvent
  13. On any dispatch: SendFirstRequestEvent; status "1"; DB persist
  14. On all skip: SkipActivity("4")

§19 — Response Message Rule
§19.1 Overview

Response_KNOX_LOCK_DEVICE: receives KNOX_PROXY_SERVICE response, maps into ResponseBase concept, appends to currActivity.Response[], sends audit, applies classic fan-in count.

§19.4 Fan-in Completion

Classic count: count($currActivity/Response[tib:right(tib:trim(ResponseCode), 3) = "000"]) == currActivity.RequestCount → returns "true" when all offers' lock requests succeed (end-suffix "000").
