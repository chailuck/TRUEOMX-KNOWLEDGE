Request_CCBS_UPDATE_SUBSCRIBER

Update subscriber offers in CCBS — dual POU+COU loop with pooling and split-charge resolution
Backend: CCBS Pattern: POU+COU Loop · Per-Offer · IntraSeq Fan-in Author: awalia-t420 Priority: 5 Generated: 2026-09-18
§1 — Overview & Purpose

This rule updates subscriber offers in CCBS for each subscriber (POU and COU). It is the most complex FM in the UPDATE_CALL_VERIFICATION flow. Key responsibilities:

  • Pooling resolution: Resolves POOLED_OFFER_INSTANCE_ID from the Agreement's ExtendedInfo based on global variable-configured prefix
  • SOC/PropValue list building: Pre-computes SOC list and split-indicator (PLG/EGI/other) for charge and event distribution
  • Per-offer fan-out: Sends one request per subscriber containing all qualifying offers (not per-offer individually)
  • Offer filtering: Skips offers with ServiceType="80"; applies offer-level PreExecCheck via GetXMLForSubscriberOfferFilterWithExtendedInfo
  • Sequence number: Requests SOC_SEQ_NO increment for number of offers + related offers

§9 — Detailed Payload Build
Two XSLT variants exist: one for POU subscribers, one for COU subscribers. They differ only in the index variables used to navigate the Customer hierarchy: POU uses $OU,$sub; COU uses $OU,$iCOU,$sub.

§9.4 Payload Structure

The ns:UpdateSubscriberRequest has this nested structure:

<ns:UpdateSubscriberRequest>
  <ns1:GetSequenceValueRequest>
    <ns1:sequenceName>SOC_SEQ_NO</ns1:sequenceName>
    <ns1:incrementByCount>count(offers) + count(relatedOffers)</ns1:incrementByCount>
  </ns1:GetSequenceValueRequest>
  <ns:UpdateSubscriberRequest>
    <ns:SubscriberIdInfo> ← SubscriberId
    <ns:ChangeSubscriberOffersWithRelatedOffersInputInfo>
      <ns:offersToAdd> ← for-each subOffersArray
        <ns:srvAgrInfo> ← dealerCode, deployMode, effectiveDate,
                        expirationDate, name(OfferName), soc,
                        serviceType, parentOfferInstanceId,
                        relatedOffers (nested)
      </ns:offersToAdd>
      <ns:ParameterInfo> ← from SubscriberOffer.ParameterInfo
      <ns:ParameterInfo> ← PLG pooling: "Agreement level offer instance ID"
      <ns:ParameterInfo> ← from RelatedOffers.ParameterInfo
      <ns:ChargeDistributionDetailsInfo> ← CHG_SPLIT_TYPE=DR/DS or SPLITS01
      <ns:EventDistributionDetailsInfo> ← EGI pooling type
      <ns:ActivityInfo> ← activityReason, optional userText
    </ns:ChangeSubscriberOffersWithRelatedOffersInputInfo>
    <ns:ActivityInfo> ← activityReason, userText, optional logicalDate in enclosedClientInfo
  </ns:UpdateSubscriberRequest>
</ns:UpdateSubscriberRequest>

§19 — Response Message Rule

§19.1 Overview

Response_CCBS_UPDATE_SUBSCRIBER uses a custom concept CCBS_UpdateSubscriberRes (not the generic ResponseBase). It appends the response and advances the IntraSeq fan-in. The old successResponseCount block is commented out.

§19.3 Response Concept Construction

Creates Concepts.FM.Response.CCBS_UpdateSubscriberRes (not ResponseBase). All 4 fields (ResponseCode, ResponseMessage, CompletionStatus, ReferenceId) are conditional — only emitted if present in eventResponse.

§19.4 Fan-in Completion

Uses IntraActivitySequencing.ActionResponseEvent(currActivity). The successResponseCount XPath logic is commented out.
