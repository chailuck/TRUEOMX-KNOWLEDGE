Request_OMX_GET_RECURRING_CHARGE

Recurring Charge Lookup — unique SOC deduplication with GoldenDB-aware dual-variant dispatch
Backend: OMX FM (GoldenDB variant: CES) Priority: 5 Pattern: FIRE-AND-FORGET Iteration: SubscriberOffers/AgreementOffers (deduplicated by SOC)
§1 — Overview & Purpose
OMX_GET_RECURRING_CHARGE retrieves the recurring charge (RC) for each unique product (SOC code) in the order. It scans all SubscriberOffers and AgreementOffers across all POU/ChildOU, deduplicates by SOC, and sends one request with the full list of unique SOC codes.
Unique iteration pattern: Unlike other FMs that iterate Accounts or Subscribers, this FM builds a deduplicated ArrayList of unique SOC codes across four paths: ChildOU.Subscriber.SubscriberOffers, ChildOU.Agreement.Offers, POU.Subscriber.SubscriberOffers, and POU.Agreement.Offers. Only SOCs passing the PreExecCheck are added. If the list is empty, the activity is skipped.
GoldenDB dispatch: If OrderData.GoldenDB = "Y" → sends to CES_GET_RECURRING_CHARGE; otherwise → OMX_GET_RECURRING_CHARGE. Both have the same payload structure but different routing/event type.
Response write-backs: For each SOC in the response's SocRecurringCharges[], writes an ExtendedInfo entry (Name="RC", Value=RecurringCharges) to every matching SubscriberOffer and AgreementOffer across all POU/ChildOU.

§7 — Key Logic Patterns
PatternDetail
SOC deduplicationArrayList offerList; Collections.add(offerList, soc) only if !Collections.contains(offerList, soc). Ensures one <soc_cd> per unique product regardless of how many subscribers use it.
PreExecCheck per offerFour helper variants: GetXMLForSubscriberOfferInChildOU, GetXMLForAgreementOfferInChildOU, GetXMLForSubscriberOffer, GetXMLForAgreementOffer. Only offers passing the check are added to the SOC list.
GoldenDB dispatchIf OrderData.GoldenDB = "Y" → CES_GET_RECURRING_CHARGE event type; else → OMX_GET_RECURRING_CHARGE. Payload structure identical.
Resubmit guardif(!isActResub) RequestCount++ — does NOT skip sending on resubmit, only skips the RequestCount increment.
Response write-back scopeSearches all 4 paths (ChildOU.Subscriber.SubscriberOffers, ChildOU.Agreement.Offers, POU.Subscriber.SubscriberOffers, POU.Agreement.Offers) for SOC match; writes RC to matching offer ExtendedInfo.

§17 — Migration Notes & Recommendations
RiskSeverityMitigation
Response always returns "true" — no success count validation. If the OMX FM returns errors for some SOCs, the activity still completes successfully MEDIUM Add response code validation per SocRecurringCharges entry in migration
GoldenDB dispatch: if GoldenDB value changes or is absent, the wrong event type is sent silently LOW Document GoldenDB values and routing table; validate at order submission time
SOC deduplication via ArrayList is memory-resident — not persistent. On resubmit the list is rebuilt from scratch, potentially re-sending already-processed SOCs MEDIUM Implement idempotent RC lookup; cache RC values in order ExtInfo to survive resubmits
Response write-back iterates all 4 paths for every SOC — O(N×M) where N=SOCs, M=all offers. Large orders may be slow LOW Consider indexing offers by SOC at order load time
Only one RC request sent for entire order (all SOCs in one payload) — if OMX FM has a per-SOC limit, large orders may fail LOW Verify OMX FM batch size limit; implement pagination if needed
