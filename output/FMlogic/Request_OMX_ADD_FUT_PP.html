Request_OMX_ADD_FUT_PP

FM Logic Documentation — OMX Add Future Price Plan (FUTPP) — ParentOU / ChildOU / Subscriber
System: OMX (Internal) Priority: 5 ForwardChain: true ActivityID: OMX_ADD_FUT_PP 4 Variants Generated: 2026-09-14
§1 — Overview & Purpose

This rule creates future price plan (FUTPP) records in OMX for all qualifying offers in a CHANGE_PP order. It iterates over four distinct node types — ParentOU Agreement, ParentOU Subscriber, ChildOU Agreement, ChildOU Subscriber — and sends one OMX_ADD_FUTURE event per offer that passes PreExecCheck.

Each event carries a futureOrderWithSoc payload that includes the future order context (nodeLevel, nodeId, futureType=FUTPP) and the primary SOC offer plus any extra FE/TR_CONTRACT_NUMBER SOCs and ParameterInfo/RelatedOffersArray children.

Four iteration variants:
  • ① ParentOU Agreement Offers — nodeLevel=3, nodeId=OUId, XSLT param: pOu
  • ② ParentOU Subscriber Offers — nodeLevel=5, nodeId=subId, XSLT param: subscriberPou
  • ③ ChildOU Agreement Offers — nodeLevel=3, nodeId=OUId, XSLT param: cOu
  • ④ ChildOU Subscriber Offers — nodeLevel=5, nodeId=subId, XSLT param: subscriberCou
[NOTE]: The two audit log OPERATION_NAME values differ between variants: ParentOU Agreement uses "OMX_ADD_FUTPP"; Subscriber and ChildOU variants use "OMX_ADD_FUT_PP". This is a naming inconsistency in the source code.

OMX-2896 FLG_SMS support

For subscriber variants (② and ④): if ExtendedInfo[Name="FLG_SMS"] exists, its value is passed as FLG_SMS_WELCOME_SUB extendedInfo in the payload — used for corporate welcome SMS.

Secondary futureSoc (FE/TR_CONTRACT_NUMBER)

For every variant, after the primary futureSoc, the XSLT adds extra futureSoc elements for any offer in the current scope that meets all three conditions:

  • ServiceType = 85
  • ExtendedInfo[Name='FE_OR_CCBS' and Value='FE']
  • boolean(ParameterInfo[ParamName = 'TR_CONTRACT_NUMBER'])

These carry type=ServiceType, subType="FUTPP", optional expireDate=ExpirationDate.

futureResourceRange (Subscriber variants only)

Subscriber variants (② and ④) append ns4:futureResourceRange elements for each ResourceRangeInfo[Action='PP'] entry on the subscriber.

§17 — Migration Notes & Recommendations

Functional Requirements

  • R1: For every qualifying offer (passing PreExecCheck) in ParentOU Agreement, ParentOU Subscriber, ChildOU Agreement, and ChildOU Subscriber scopes, create a FUTPP future order record with nodeLevel=3 (OU) or 5 (Sub).
  • R2: customerType must be derived by ASCII-decoding CustomerTypeInfo/Type via OMXUtils.asciiCodeToText().
  • R3: Secondary futureSoc must be added for any ServiceType=85/FE/TR_CONTRACT_NUMBER offer in the same scope.
  • R4: Subscriber variants must carry futureResourceRange entries for ResourceRangeInfo[Action='PP'] items.
  • R5: ChildOU variants must add OU_ID extendedInfo always; Subscriber variants add SUB_ID, MOBILE_NO, FLG_SMS_WELCOME_SUB (conditional).
