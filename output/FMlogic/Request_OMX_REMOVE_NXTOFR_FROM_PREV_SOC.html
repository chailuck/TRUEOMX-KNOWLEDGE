Request_OMX_REMOVE_NXTOFR_FROM_PREV_SOC

TIBCO BusinessEvents FM Logic — Remove Next Offer from Previous SOC (Future Order Cleanup)
Priority: 5 ForwardChain: true Backend: OMX Internal FM Operation: RemoveNextOfferFromPrevSoc Dispatch: sendEventImmediate (parallel) Fan-out: 4 loops (POU/COU × Agreement/Subscriber) Fan-in: ResponseCode suffix "000" Author: SathidP-PC
§1 — Overview & Purpose

This rule cleans up future order (NXTOFR) linkages on a SOC. When an offer is being removed from a subscriber or agreement, any scheduled "next offer" pointer on the previous SOC must be cleared. The rule sends one OMX_REMOVE_NXTOFR_FROM_PREV_SOC request per qualifying offer across four traversal paths: POU Agreement Offers, POU Subscriber Offers, COU Agreement Offers, and COU Subscriber Offers.

The payload schema (ns4:futureOrderAll) carries a fixed futureSoc.code = "-" which signals the system to remove the next-offer link, and futureSoc.previousSoc = $soc identifies which SOC's future link to clear.

⚠ BUG — Resubmission skip never fires [HIGH]
The skip check compares Response[ReferenceId == pOu.OUId/cOu.OUId/subscriberId], but the response concept (OMX_RemoveNextOfferFromPrevSocRes) does NOT map a ReferenceId field. ReferenceId will always be empty, so no response will ever match — resubmission will always re-dispatch all offers even if they already succeeded.
5 dead variables declared at rule top but never passed to any XSLT: futureType, requestedDate, requestedBy, requestedByUser, logicalDate. [MEDIUM]
IsEnableUserPass feature: All 4 XSLTs include a conditional UserName/PassWord block gated by a global variable — credential injection for backends requiring HTTP Basic auth.

§5 — Execution Flow Diagram
  1. Compute isActResub; read Concepts.OM.LogicalDate (logicalDate dead variable)
  2. Set dead vars: futureType="NXTOFR", requestedDate, requestedBy, requestedByUser
  3. Loop ①: POU Agreement Offers — per pOu.Agreement.Offers[iPouOffer]
  4. Filter: FE_OR_CCBS read but NOT filtered (Agreement offers always eligible)
  5. PreExecCheck via GetXMLForAgreementOffer; if chkRes=="true"
  6. Resubmit skip: Response[ReferenceId==pOu.OUId and CompletionStatus==2] — never matches (ReferenceId not set in response) [BUG]
  7. Build Variant ①: nodeLevel=3, nodeId=pOuId; dispatch sendEventImmediate; audit log
  8. Loop ②: POU Subscriber Offers — per subscriberPou.SubscriberOffers[iPouSubOffer]
  9. Filter: source must equal "FE" (CCBS-sourced sub offers skipped)
  10. Resubmit skip: Response[ReferenceId==subscriberPou.SubscriberId] — never matches [BUG]
  11. GetNextPricePlan gate: only dispatch if !IsBlankOrStringNull(nxtOfferName)
  12. Build Variant ②: nodeLevel=5, nodeId=subId, conditional OfferInstanceId
  13. Loop ③: COU Agreement Offers — per cOu.Agreement.Offers[iCouOffer]
  14. Filter: FE_OR_CCBS read but NOT filtered (same as Loop ①)
  15. PreExecCheck via GetXMLForAgreementOfferInChildOU
  16. Build Variant ③: nodeLevel=3, nodeId=couId; no OfferInstanceId; no nxtOfferName gate
  17. Loop ④: COU Subscriber Offers — per subscriberCou.SubscriberOffers[iCouSubOffer]
  18. Filter: source must equal "FE" (same as Loop ②)
  19. Build Variant ④: nodeLevel=5, nodeId=subCouId; no OfferInstanceId; no nxtOfferName gate
  20. If any dispatched: Status="1", SendDataToDB; else SkipActivity("4")
  21. On exception: HandleActivityException

Design inconsistency [MEDIUM]: POU Subscriber applies GetNextPricePlan gate — dispatches only if a next price plan is found in SocProperties. COU Subscriber has no equivalent gate — all qualifying COU subscriber offers are dispatched unconditionally. This asymmetry may cause spurious removals on COU subscribers.

FE_OR_CCBS filter behaviour

All four loops read the FE_OR_CCBS ExtendedInfo from each offer into source (defaulting to "FE"). However, only the Subscriber loops (② and ④) gate dispatch on String.equals(source, "FE"). Agreement loops (① and ③) read source but never use it in their dispatch condition — CCBS-sourced agreement offers are always processed.
