Request_CVSS_GET_EXISTING_PRODUCT

CVSS Existing Product Count — minimal fire-and-forget with Account.ProductCount write-back
Backend: CVSS Author: awalia-t420 Priority: 5 Pattern: FIRE-AND-FORGET (no IntraActivitySequencing) Fan-in: RequestCount count
§1 — Overview & Purpose
CVSS_GET_EXISTING_PRODUCT retrieves the count of existing CVSS products for each Account. The result updates Account.ProductCount, which is consumed by downstream credit evaluation logic.
Fire-and-forget pattern: Uses Event.Ext.sendEventImmediate(reqEvent) + manual RequestCount++. Fan-in uses the OLD count-based pattern: count("000" responses) == RequestCount — NOT IntraActivitySequencing.
Minimal payload: Only two fields — ban (Account.AccountID) and productId=1 (hardcoded). No account subtype, no customer details.
Response write-back: Looks up Account by extId pattern "A:"+JMSCorrelationID+":"+RefID and sets acct.ProductCount from response count field.

§17 — Migration Notes & Recommendations
RiskSeverityMitigation
Uses OLD fan-in pattern (count "000" responses == RequestCount) — inconsistent with other FMs that migrated to IntraActivitySequencing MEDIUM Migrate to IntraActivitySequencing in a future refactor; document the inconsistency
Account lookup uses extId pattern "A:"+JMSCorrelationID+":"+RefID — requires specific extId format at account concept creation time MEDIUM Document Account concept extId format; ensure it is consistent with CVSS response correlation
productId hardcoded to 1 — undocumented constant. If CVSS changes product IDs, this breaks silently LOW Externalise productId to global variable or order parameter
result_count, statusCode, statusMessage are captured in the response concept but only ProductCount is written back to the order — the other fields are available for debugging but not persisted LOW Consider logging statusCode/statusMessage on non-success responses in migration
