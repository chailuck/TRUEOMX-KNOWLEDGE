Request_SBM_BUY_DATA_PACK

TIBCO BusinessEvents — SBM Data Pack Purchase (IntraActivitySequencing / Dual Payload / Dynamic Offer Injection)
Author: Puttaporn-PC Priority: 5 JMS Event: SBM_DO_SERVICE Pattern: IntraActivitySequencing throttled dispatch Lines: 191 (request) + 440 (response)
§1 — Overview & Purpose
Unique dispatch pattern — IntraActivitySequencing: Unlike most OMXFM rules that use Event.Ext.sendEventImmediate() to fan out all requests simultaneously, SBM_BUY_DATA_PACK uses IntraActivitySequencing.ActionRequestEvent() to queue events for throttled, sequential dispatch — SendFirstRequestEvent() fires only the first queued event. Subsequent events are released as each response arrives via ActionResponseEvent(). This serializes SBM calls to avoid flooding the SBM backend.

This FM invokes the SBM doServiceArrayRequest API to purchase a data pack for each qualifying subscriber offer. The payload is a composite: an optional CheckPackAllowRequest (validates pack eligibility) followed by a required DoServiceRequest (triggers the purchase). The response includes per-offer data info (charge amount, speed, dates) extracted from an HTML-entity-encoded extra_xml string, plus optional instructions to cancel or expire related packs and inject new BL_CREATE_CHARGE sub-offers into working memory.

§4.2 IntraActivitySequencing Key Difference

  • Standard OMXFM pattern: Event.Ext.sendEventImmediate(reqEvent) + RequestCount++ = all events dispatched immediately in parallel (fan-out)
  • SBM_BUY_DATA_PACK pattern: Event.assertEvent(reqEvent) + IntraActivitySequencing.ActionRequestEvent(reqEvent, orderCurrentActivity) — events are queued; only the FIRST is sent by SendFirstRequestEvent(); each response triggers the next via ActionResponseEvent()
  • The RequestCount is maintained internally by IntraActivitySequencing

§4.3 POU vs COU RefId Double-Colon

POU RefId: pOuRefId + ":" + ":" + refId + ":" + offer.Soc — produces e.g. "POU123::SUB456:SOC789".
COU RefId: pOuRefId + ":" + cOuRefId + ":" + sub.RefId + ":" + offer.Soc — produces e.g. "POU123:COU456:SUB789:SOC012".
The double colon in POU is intentional (cOuRefId = blank) — the response splits on ":" and maps positions [0]=POU, [1]=COU (blank for POU), [2]=Sub, [3]=SOC.

§19 — Response Message Rulefunction (Response_SBM_BUY_DATA_PACK)

§19.1 Overview

The response rulefunction is significantly more complex than a standard fan-in handler. It parses an HTML-entity-encoded extra_xml field from SBM, populates offer DataInfo, dynamically injects new pack_cancel and pack_expire sub-offers into the subscriber's SubscriberOffers, and optionally creates a BL_CREATE_CHARGE sub-offer (ServiceType="79") for downstream billing.

§19.3 RefId Parsing

String[] refIDs = String.split(eventResponse.RefID, ":");
pOuRefID = refIDs[0]    // Parent OU RefId
cOuRefID = refIDs[1]    // Child OU RefId (blank "" for POU offers)

Lookup path: match POU RefId → POU Subscriber RefId → Offer SOC. If cOuRefID is blank → POU path. If non-blank → COU path.

§19.6 pack_cancel → Immediate Cancel Sub-Offer Injection

If pack_cancel is non-blank (comma-separated list of SOC codes):

  1. Tokenize by ","
  2. For each code: create SubscriberOffers concept: OfferName=code, ServiceType="86", Action="REMOVE"
  3. Add ExtendedInfo: FE_OR_CCBS="SBM", EXP_TYPE="IM"
  4. If in POU: Soc from existing CCBS offer matching the cancel code
  5. Append to subscriber.SubscriberOffers[]
  6. Set areadyAddPackCancel=true (typo: "aready") to prevent duplicate injection across SOC matches

§19.7 pack_expire → Future Expiry Sub-Offer Injection

If pack_expire is non-blank:

  1. Load LogicalDate → compute nextBillDate = GetNextBillDate(logicalDate, BillCycleNo)
  2. Create SubscriberOffers: ExpirationDate=nextBillDate, OfferName=pack_expire, ServiceType="86", Action="REMOVE", Soc from original offer
  3. Add ExtendedInfo: FE_OR_CCBS="SBM", EXP_TYPE="FUT", EXP_DATE_VALUE=nextBillDate
  4. Append to subscriber.SubscriberOffers[]

§19.8 BL_CREATE_CHARGE Sub-Offer Injection

If featureCode from extra_xml is non-blank:

  1. Create SubscriberOffers: OfferName=featureCode, ServiceType="79" (BL charge type), Soc="-1"
  2. Add ExtendedInfo: AMOUNT=chargeAmt, FE_OR_CCBS=source (propagates FE/CCBS from original offer)
  3. Append to subscriber.SubscriberOffers[]
A commented-out line exists in both POU and COU paths showing the original intent to add via the full indexed path: // orderRequest.OrderData.Customer.ParentOU[i].Subscriber[j].SubscriberOffers[...] = subOffer;. The active line uses the local subscriber variable directly — equivalent but more concise.

§19.10 Fan-In Completion

Uses IntraActivitySequencing.ActionResponseEvent(currActivity). Returns "true" when all queued events have received responses (triggers NextActivity); "false" while still waiting. This also fires the NEXT queued request event if any remain (sequential throttling).

§17 — Migration Notes & Recommendations

Functional Requirements

  • R1 — Throttled sequential dispatch via IntraActivitySequencing; not parallel fan-out
  • R2 — On resubmit: purge pending requests before re-queuing
  • R3 — Credentials vary by IntegrationMethod: BATCH vs ONLINE endpoints
  • R4 — checkPackAllowFlg: if "Y" (default) include CheckPackAllowRequest block; "N" omits it; isActResub forces it regardless
  • R5 — RefId encoding: POU = pOu::sub:soc (double colon); COU = pOu:cOu:sub:soc
  • R6 — Response parses HTML-entity-encoded extra_xml via string manipulation (not XML parser)
  • R7 — pack_cancel → inject immediate-cancel sub-offers (ServiceType="86", Action="REMOVE", EXP_TYPE="IM")
  • R8 — pack_expire → inject future-expiry sub-offer with nextBillDate as ExpirationDate
  • R9 — BL_CREATE_CHARGE injection: if featureCode from SBM → create ServiceType="79" sub-offer with AMOUNT ExtendedInfo
  • R10 — expDate handling depends on omxFut (EXP_TYPE from OMX_CAL_OFFER_FUT_DATE): IM path sets offer.ExpirationDate; FUT path only adds SBM_NO_PROVISIONING (no date mutation)
  • R11 — OMX-2970: SBM_TRX_ID ExtendedInfo written when transaction_id present AND source=="FE"
  • R12 — Fan-in sequencing: ActionResponseEvent() returns "true" only when all queued requests have responses
