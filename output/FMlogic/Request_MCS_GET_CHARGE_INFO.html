Request_MCS_GET_CHARGE_INFO

Per-offer charge information retrieval from MCS — fan-out per subscriber offer with 3-part compound RefID (subRefId:Soc:FE_OR_CCBS), idempotent ExtendedInfo enrichment
Target: MCS (Subscription Management) Pattern: Per-offer fan-out forwardChain: true Author: DESKTOP-995HR2V Generated: 2026-08-04
§1 Overview & Purpose

This FM retrieves charge information (price, VAT amount, charge flag, expiration date) from MCS for each SubscriberOffer across POU and COU subscribers. It fires one event per offer per subscriber, using a 3-part compound correlation key (subRefId:Soc:FE_OR_CCBS) that allows per-offer deduplication on resubmit. The response enriches the matching offer with AMOUNT, IS_CHARGE, and AMOUNT_IN_VAT ExtendedInfo entries, and optionally sets offer.ExpirationDate.

Key differentiator: The compound RefID (subRefId:Soc:FE_OR_CCBS) enables offer-level resubmit dedup — before firing, the rule checks existing responses for a matching RefID with CompletionStatus == 2. This is distinct from standard RequestCount-based resubmit guards.

§6 Rule Action (THEN) — Step-by-Step Logic

§6.1 — 3-Part Compound Correlation Key

Unique to MCS_GET_CHARGE_INFO: The RefID is a colon-delimited 3-part key:
offerRefId = pSubRefId + ":" + offer.Soc + ":" + filter
where filter = offer/ExtendedInfo[Name="FE_OR_CCBS"]/Value
This allows the response handler to unambiguously locate the exact offer being updated, including distinguishing FE vs CCBS variants of the same SOC.

§6.2 — Per-Offer Resubmit Dedup Check

boolean reqSuccess = false; for(int iResp = 0; iResp < orderCurrentActivity.Response@length; iResp++) { if(String.equals(orderCurrentActivity.Response[iResp].ReferenceId, offerRefId) && orderCurrentActivity.Response[iResp].CompletionStatus == 2) { reqSuccess = true; } } if (!reqSuccess) { // proceed with PreExecCheck + fire event }

This check is independent of isActResub. An offer with a matching response (CompletionStatus==2) is silently skipped even on the first run if a prior execution already succeeded.

§6.3 — PreExecCheck Helpers (FilterWithExtendedInfo variants)

ContextHelper Function
POU Subscriber offerGetXMLForSubscriberOfferFilterWithExtendedInfo(orderRequest, pSubRefId, offer.Soc, filter)
COU Subscriber offerGetXMLForSubscriberOfferInChildOUFilterWithExtendedInfo(orderRequest, cSubRefId, offer.Soc, pOuRefId, filter)
These are extended variants that include the FE_OR_CCBS filter value in the serialized XML context, unlike the standard GetXMLForSubscriberOffer used in other FMs.

§6.4 — isSkipped Logic

isSkipped starts true. It is set to false the moment any event is sent. If the outer loop completes without sending any events (all offers failed PreExecCheck or reqSuccess), SkipActivity("4") is called.
§7 Data Extraction — FE_OR_CCBS Filter

The filter value is extracted per-offer using an inline XPath evaluation:

String filter = XPath.evalAsString("xpath://<expr>$offer/ExtendedInfo[Name=\"FE_OR_CCBS\"]/Value</expr>...");

This value (e.g., "FE", "CCBS", "CRM") is appended to the correlation key and later used in the response to filter the correct offer variant.

§19 Response Message Rule

§19.1 — Overview

The response handler parses the 3-part RefID to locate the target subscriber/offer, then idempotently appends AMOUNT, IS_CHARGE, and AMOUNT_IN_VAT ExtendedInfo entries and optionally sets offer.ExpirationDate. The triple before-write checks prevent duplicate ExtendedInfo entries on retry/resubmit.

§19.7 — Fan-in Completion Logic

int successResponseCount = XPath.evalAsInt( "count($currActivity/Response[tib:right(tib:trim(ResponseCode), 3) = '000'])"); if(currActivity.RequestCount == successResponseCount) { return "true"; } else { return "false"; }

Standard "000" success count fan-in — returns "true" only when all per-offer requests have received a "000" response. One failed offer (non-"000" ResponseCode) will cause the fan-in to wait indefinitely.
