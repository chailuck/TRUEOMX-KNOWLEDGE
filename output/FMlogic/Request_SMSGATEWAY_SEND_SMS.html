§1Overview & Purpose

Purpose

Constructs and dispatches ns:SMSRequest JMS events to the SMS Gateway to notify subscribers of order-related changes (price plan adds/changes, IDD/IR roaming activation, discount and topping additions/removals).

Architecture summary: Two outer loops (ChildOU Subscriber and ParentOU Subscriber) each classify the subscriber's offers then send one or more SMS events — one per qualifying offer type. Three distinct XSLT variants produce the payload depending on context. The response RF uniquely writes ResponseCode/ResponseMsg back to the Subscriber concept.

§5Execution Flow Diagram

1
Outer loop — ChildOU path: iterate ParentOU[i] → ChildOU[k] → Subscriber[j]
2
ResSuccess check: skip subscriber if prior response already has CompletionStatus=2 for this RefId
3
GetXMLForSubscriber: extract subscriber XML for PreExecCheck evaluation
4
PreExecCheck gate: skip subscriber if gate returns false
5
Offer classification: scan subscriber offers → classify into pp / contract / rmvx / iddOffL / irOffL / discOffL / toppOffL buckets
6
Date/duration calculations: ppEffDT from EffectiveDate or OfferOriginalEffectiveDate (Bangkok TZ); GetPPDurationMonth; GetBillCycle; GetPPExpirationDate; Thai month conversion for Language=TH
7
Per-offer SMS dispatch (ChildOU Offer variant): for each qualifying IDD/IR/Discount/Topping offer → set offerSMSType → send XSLT variant ①; RequestCount++; audit if AllowWriteLog
8
Outer loop — ParentOU path: iterate ParentOU[i] → Subscriber[j] (lines ~508+)
9
Same ResSuccess / PreExecCheck / offer-classification logic for ParentOU subscribers
10
Branch by OrderType:
  • OrderType ∈ {3,69,70,11018} AND qualifying offers → ParentOU Offer variant ②: RequestCount++; audit unconditionally
  • Otherwise → Generic PP-only variant ③: RequestCount++; audit if AllowWriteLog
11
Fan-in wait: response RF counts successful responses; when successResponseCount == RequestCount → activity completes

§6Rule Action (THEN) — Step-by-Step Logic

Loop 1 — ChildOU Subscriber (lines 27–507)

Triple-nested loop: for i in ParentOU → for k in ChildOU → for j in Subscriber

Sub-stepLogic
Get RefIdString refId = subscriber.RefId;
Skip checkScan orderCurrentActivity.Response[]: if any entry has ReferenceId == refId && CompletionStatus==2 → set reqSuccess=true → skip
XML extractionGetXMLForSubscriber(orderRequest, refId)
PreExecCheckIf nextAct.PreExecCheck.length > 0: evaluate XPath against subscriber XML; skip if not "true"
LanguageFrom SubscriberGeneralInfo.Language; default "TH"
PP classificationSubscriberOffer where ServiceType='80' AND (FE_OR_CCBS=FE or blank) → pp offer name; subscriberPP object
Contract classificationSubscriberOffer where TR_CONTRACT_IND=Y AND (FE_OR_CCBS=FE/BRMS/blank) → contract offer name
RMVXOfferName = RMVX00000000001 → store rmvxProps for duration calculation
IDD/IR/Discount/ToppingFor FE/BRMS/BRMS_REMOVE or (OrderType=11018 + INJECT_OFFER): classify into iddOffL, irOffL, discOffL, toppOffL lists (see §7)
Date calculationsppEffDT = EffectiveDate ?? OfferOriginalEffectiveDate (Bangkok); GetPPDurationMonth(rmvxProps, subscriberPP); GetBillCycle; GetPPExpirationDate
Per-offer sendFor each offer in iddOffL/irOffL/discOffL/toppOffL: build offerSMSType string → dispatch XSLT variant ①; RequestCount++ (if !isActResub); isSkipped=false; audit if AllowWriteLog
Loop 2 — ParentOU Subscriber (lines 508–~1050)

Double-nested loop: for i in ParentOU → for j in Subscriber

Same ResSuccess / PreExecCheck / offer-classification logic as Loop 1. Key difference: branch by OrderType at point of dispatch.
BranchConditionVariantAudit
Offer SMSOrderType ∈ {3,69,70,11018} AND qualifying offers presentXSLT variant ② (ParentOU offer)Unconditional (bug: should be gated)
Generic PP SMSOtherwise (OrderType not in set, or no qualifying offers)XSLT variant ③ (PP-only)Gated by AllowWriteLog(OrderType)
Bug: XSLT variant ② (lines 474–485) sends the audit log unconditionally — no AllowWriteLog(OrderType) guard. Variants ① and ③ both correctly gate the audit. This means OrderType 3/69/70/11018 always generates audit entries regardless of the AllowWriteLog policy.
isActResub guard

If isActResub == true (the activity is being resubmitted), RequestCount++ is skipped for each dispatch. This prevents double-counting on retry scenarios. isSkipped = false is still set.

§12Activity Status Management

This rule does not directly modify activity status. Status transitions are managed by the response RF (fan-in completion → activity moves to COMPLETED) and the orchestration layer.

FlagSet whenPurpose
isSkippedSet false after each dispatchTracks whether activity sent any requests

§13Exception / Error Handling

Standard OMXFM exception pattern: HandleActivityException is called in the catch block with the exception detail. The activity transitions to an error state, and the orchestrator can trigger retry/resubmission logic.

The reqSuccess skip check (checking CompletionStatus==2 for prior responses) is the per-subscriber resumption guard against duplicate SMS sends.

§19Response Message Rule

§19.1 Overview

Parses the SMS Gateway reply, creates a SMSGATEWAY_SendSMSRes concept instance, gates audit logging via AllowWriteLog, writes response data back to the originating Subscriber concept, and drives fan-in completion.

Unique among OMXFM response RFs: both request AND response audit are gated by AllowWriteLog(OrderType). Additionally, the response RF writes ResponseCode and ResponseMsg back to the Subscriber concept — no other OMXFM response RF does this.

§19.4 Subscriber Concept Writeback

After appending the response concept, the RF looks up the originating Subscriber via:

  sub.ResponseMsg  = eventResponse.ResponseMsg;

The CSUB: fallback handles ChildOU Subscriber scenarios where the extId was created with the CSUB prefix. Primary lookup uses SUB: (ParentOU Subscriber path).
