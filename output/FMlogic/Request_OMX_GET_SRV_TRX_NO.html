Request_OMX_GET_SRV_TRX_NO

AA Service Transaction Number — Batch Sequence Fetch with Per-Subscriber Distribution
Priority: 5 forwardChain: true Author: mranade-T420 Pattern: Single Batch Request Backend: OMX Sequence Service (AA_TRX_NO_SEQ) Generated: 2026-07-27
§1 — Overview & Purpose

This rule allocates AA service transaction sequence numbers (from sequence AA_TRX_NO_SEQ) for downstream AA provisioning. It counts eligible subscribers first, then requests that exact number of sequence values in a single batch call. The response distributes one sequence number per subscriber in iteration order.

Single batch request pattern: Like GET_SPECIAL_OFFER_INDICATOR, this uses Event.Ext.sendEventImmediate with a single request carrying amount = countAllSub. The response returns all values in a GetSrvTrxNoResponse/sequenceValue[] array, which the response handler iterates in lock-step with the subscriber loop (sequenceValue[$countSrvTrxNo+1]).
AA_CHECK_CONFIRMATION pre-wiring: The response handler scans ProcessFlow.Activities[] for AA_CHECK_CONFIRMATION (same Parameter[0] / network command type) and sets its RequestCount = countSrvTrxNo. This pre-seeds the downstream fan-in counter so AA_CHECK_CONFIRMATION knows how many successful responses to wait for.
Two activity parameters:
  • Parameter[0] — network command type (e.g., NAC, DSD, or INAC / IDSD if rewritten by OMX_TRANSFORM_NETWORK_CMD_TO_IOT). Written as SrvTrxTp on each SrvTrxNoInfo.
  • Parameter[1] — SOURCE_OR_TARGET filter (e.g., SOURCE or TARGET). Only subscribers with matching ExtendedInfo[SOURCE_OR_TARGET] are counted and assigned sequence numbers. If absent → all subscribers included.

§19 — Response Message Rule

§19.1 — Overview

The response is a single batch reply containing all requested sequence values in GetSrvTrxNoResponse/sequenceValue[]. The handler iterates subscribers (same ParentOU + ChildOU loops, same eligibility filter) and assigns values by position index (countSrvTrxNo). Two concept types are created per subscriber:

  • OMX_GetSrvTrxNoRes — stored in currActivity.Response[]
  • SrvTrxNoInfo — stored in subscriber.SrvTrxNoInfo[] for downstream AA use

§17 — Migration Notes & Recommendations

Functional Requirements

  • R1 — The pre-count step (request) and the distribution step (response) must apply the same eligibility filter (SOURCE_OR_TARGET + PreExecCheck) to ensure amount matches the number of subscribers that will receive values.
  • R2 — Sequence values are assigned by iteration order — the N-th eligible subscriber gets sequenceValue[N]. Migration must preserve this iteration order (ParentOU subscribers first, then ChildOU subscribers for each ParentOU).
  • R3 — AA_CHECK_CONFIRMATION.RequestCount pre-wiring is a critical side effect. In migration, this initialization must happen at the equivalent point (after all SrvTrxNo values are distributed).
  • R4 — Parameter[0] is the network command type and may have been transformed from e.g., "NAC" to "INAC" by OMX_TRANSFORM_NETWORK_CMD_TO_IOT earlier in the flow. Migration must handle both forms.
  • R5 — Audit logging uses AllowWriteLog(OrderType) — not the standard WritePayload gate. Some order types may suppress all logging.
