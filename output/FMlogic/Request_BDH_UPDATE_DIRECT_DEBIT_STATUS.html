Overview & Purpose

This rule is triggered when an order's process flow reaches the BDH_UPDATE_DIRECT_DEBIT_STATUS activity in the WAITING state. It constructs a JMS request message and dispatches it to the BDH (Bank Direct Handle) system to cancel all Direct Debit mandates associated with the customer's accounts.

Business Intent: When a subscriber order is being processed (e.g., number porting, service cancellation, or SIM swap), any existing Direct Debit mandate must be cancelled with the bank before provisioning proceeds. This rule automates that cancellation by sending a bulk request — one requestList entry per account — with a hardcoded reason code of DDMREQ (Direct Debit Mandate Request) and status C (Cancel).

§ 4

Rule Conditions (WHEN)

All four conditions must be simultaneously true for this rule to fire. They form a precise triple-lock: activity pointer, activity ID, and activity state.


Condition 1 — Activity Pointer Match
orderCurrentActivity@extId == orderRequest.ProcessFlow.NextActivityName
Ensures the candidate activity is exactly the one the order's process flow is currently pointing to. Prevents spurious rule firings from other WAITING activities in Working Memory.
Condition 2 — Activity Identity Check
orderCurrentActivity.ActivityID == "BDH_UPDATE_DIRECT_DEBIT_STATUS"
Confirms the matched activity is specifically the BDH Update Direct Debit Status step. Prevents other activities with WAITING status from accidentally triggering this rule.
Condition 3 — Process Flow Consistency Guard
orderRequest.ProcessFlow.NextActivityID == "BDH_UPDATE_DIRECT_DEBIT_STATUS"
Secondary cross-check on the ProcessFlow concept itself (not just the Activity concept). Guards against Working Memory inconsistency where the pointer was updated but the ID wasn't.
Condition 4 — Readiness Gate
orderCurrentActivity.Status == "WAITING"
The activity must be in WAITING state. Activities in IN_PROGRESS, SUCCESS, ERROR, or SKIPPED states will not trigger this rule, preventing duplicate sends.
§ 5

Execution Flow Diagram

1
Resubmit Flag Evaluation
Check if orderCurrentActivity.RequestCount > 0 AND orderRequest.IsOrderResubmitted is true → set isActResub. This flag prevents duplicate RequestCount increments during order resubmission.
2
Load Activity Config & PreExecCheck
Retrieve the Activity concept using Instance.getByExtIdByUri(orderRequest.ProcessFlow.NextActivityName). Read its PreExecCheck XPath expression string. Initialize chkRes = "true" and isSkipped = true.
3
Conditional PreExecCheck Evaluation
If String.length(nextAct.PreExecCheck) > 0: serialize orderRequest to XML string via Instance.serializeUsingDefaults(), then evaluate chkXPath via XPath.execute() against the serialized XML. The result overrides chkRes. If empty, chkRes remains "true" (execute always).
4
Build & Send BDH Request Event
(Only if chkRes == "true") — Execute XSLT to build BDH_UPDATE_DIRECT_DEBIT_STATUS event. Iterate all Customer/Account entries with non-empty AccountID; emit one requestList element per account with static reasonCode=DDMREQ and status=C. Send via Event.Ext.sendEventImmediate().
5
Increment Request Counter (if new request)
If !isActResub, increment orderCurrentActivity.RequestCount++. Prevents double-counting during resubmissions.
6
Emit Audit Log
Capture a nanosecond timestamp pid = System.nanoTime(). Build and send an OMXESB Logger event via Event.Ext.sendEventImmediate() with OPERATION_NAME=BDH_UPDATE_DIRECT_DEBIT_STATUS, LOG_LEVEL=INFO, and AUDIT_TRACE="Request Sent for BDH_UPDATE_DIRECT_DEBIT_STATUS". Optionally copies the full request payload if WritePayload=true.
7
Set isSkipped = false
Marks that the request was sent (not skipped). Used by the downstream status-transition branch.
8
Activity Status Transition (Branch)
If NOT skipped: orderCurrentActivity.Status = "IN_PROGRESS" → call SendDataToDB(orderRequest).
If skipped (chkRes ≠ "true"): call SkipActivity(orderRequest, orderCurrentActivity, "4") → sets status to SKIPPED and advances the process flow to the next eligible activity.
!
Exception Path
Any exception in the try block is caught and routed to HandleActivityException(orderRequest, orderCurrentActivity, ae, "") — sets activity status to ERROR, logs to ErrorLog channel, and activates the exception activity if configured.

6.3 Event Build & Send

When chkRes == "true":

  1. An Events.OMConsumers.OMXFM.Request.BDH_UPDATE_DIRECT_DEBIT_STATUS event is constructed using inline XSLT transformation against $orderRequest.
  2. The event extId is assigned via OMXUtils:generateTrackingID() (custom TIBCO function).
  3. JMS header fields (JMSPriority, JMSCorrelationID) and metadata fields (OrderID, RefID, OrderType) are conditionally mapped.
  4. The payload iterates over all Customer/Account entries, emitting one ns1:requestList per account with non-empty AccountID.
  5. Event.Ext.sendEventImmediate(reqEvent) dispatches the message to the JMS queue synchronously in the current thread.

§ 13

Exception / Error Handling

The entire THEN body is wrapped in a single try { ... } catch (Exception ae) { ... } block. Any runtime exception (JMS send failure, XSLT error, null pointer, etc.) is routed to:

RuleFunctions.Helpers.HandleActivityException(orderRequest, orderCurrentActivity, ae, "");

HandleActivityException performs the following:

  1. Reads global variables to compose a structured response code: {ComponentName}{ServiceCode}{OperationCode}{Severity}{ErrorCode} → e.g., OM010103999
  2. Sets orderCurrentActivity.Status = "ERROR"
  3. Writes orderCurrentActivity.ResponseCode and ResponseMessage
  4. Sets orderRequest.OrderStatus to FAILED (status 3)
  5. Calls RuleFunctions.Helpers.SetResponseCode() to propagate the error
  6. Emits an audit log to /Channels/LogConnection/ErrorLog at ERROR level, including exception type, message, and stack trace
  7. If orderCurrentActivity.ExceptionActivity is non-blank: retrieves that activity, sets it to WAITING, and redirects the process flow — enabling a configurable exception-handling path
  8. Calls SendDataToDB(orderRequest) to persist the error state

§ 17

Migration Notes & Recommendations

17.1 Functional Requirements
  • The migrated system must send a BDH_UPDATE_DIRECT_DEBIT_STATUS cancellation request to BDH for each active account in the order's Customer/Account array when this activity step is reached.
  • The request must carry the hardcoded cancellation instruction: reasonCode = "DDMREQ", status = "C" per account. If BDH's schema evolves, these values may need to be externalised to configuration.
  • Request correlation must be maintained via JMSCorrelationID = OMXTrackingId so the async BDH response can be matched back to the correct order.
  • A configurable PreExecCheck skip mechanism must be preserved — it allows conditional bypass of BDH without code changes.
  • The RequestCount field must not be incremented during order resubmission (when IsOrderResubmitted = true and count already > 0).
  • An INFO-level audit log entry must be emitted after every successful request dispatch, including the nanosecond process ID and optionally the full request payload (governed by WritePayload flag).
  • Activity status must transition: WAITING → IN_PROGRESS on send, SKIPPED if PreExecCheck fails, ERROR if an exception occurs. SUCCESS is set by the Response handler.
  • On exception, the activity and order must be marked ERROR, the error must be logged to the ErrorLog channel, and if an ExceptionActivity is configured, the flow must be rerouted to it.
17.2 Design Risks
RiskSeverityMitigation
Hardcoded reasonCode="DDMREQ" and status="C" — no dynamic control MEDIUM During migration, externalise these to a configuration table or ProcessConfig parameters to allow future flexibility without code redeployment.
Accounts with empty AccountID are silently skipped via xsl:if — no warning logged LOW Add observability: log a warning when accounts are skipped due to empty AccountID to aid debugging of incomplete orders.
An order with zero valid accounts produces an empty UpdateDirectDebitStatusReq payload MEDIUM Add a guard: if no accounts are present, either skip the activity entirely or fail with a meaningful error code. The current code sends an empty request to BDH, which may cause unexpected BDH-side behaviour.
Async JMS pattern — no timeout/retry logic in this rule MEDIUM Ensure the Response rule has a timeout mechanism (TTL on event, expiry action) and that TTL expiry triggers retry or exception flow. The BDH_UPDATE_DIRECT_DEBIT_STATUS event defines an expiryAction that should be verified.
XSLT inline in rule source — hard to unit-test or version independently LOW In the target architecture, externalise XSLT to a separate template file or use a mapping framework with independent test coverage.
SendDataToDB is a very large function (~660KB) — coupling risk MEDIUM In microservices migration, replace with a dedicated persistence service or event sourcing pattern. Avoid carrying this monolithic DB function as-is.

Source: OMX-OM/Rules/OMConsumers/OMXFM/Request/Request_BDH_UPDATE_DIRECT_DEBIT_STATUS.rule

/**
 * @description
 * @author DESKTOP-995HR2V
 */
rule Rules.OMConsumers.OMXFM.Request.Request_BDH_UPDATE_DIRECT_DEBIT_STATUS {
    attribute {
        priority = 5;
        forwardChain = true;
    }
    declare {
        Concepts.OrderRequest.OrderRequest orderRequest;
        Concepts.OM.ProcessConfig.Activity orderCurrentActivity;
    }
    when {
        orderCurrentActivity@extId == orderRequest.ProcessFlow.NextActivityName;
        orderCurrentActivity.ActivityID == "BDH_UPDATE_DIRECT_DEBIT_STATUS";
        orderRequest.ProcessFlow.NextActivityID == "BDH_UPDATE_DIRECT_DEBIT_STATUS";
        orderCurrentActivity.Status == "WAITING";
    }
    then {
        boolean isActResub = (orderCurrentActivity.RequestCount > 0
                             && orderRequest.IsOrderResubmitted);

        try {

                String sXML = Instance.serializeUsingDefaults(orderRequest);
                chkRes = XPath.execute("/(" + chkXPath + ")", sXML,
                    "ns0=www.tibco.com/be/ontology/Concepts/OrderRequest/OrderRequest");
            }

            if(String.equals(chkRes, "true")) {

                Events.OMConsumers.OMXFM.Request.BDH_UPDATE_DIRECT_DEBIT_STATUS reqEvent =
                    Event.createEvent("xslt://{{/Events/OMConsumers/OMXFM/Request/BDH_UPDATE_DIRECT_DEBIT_STATUS}}"

                    "xslt://{{/Events/OMConsumers/OMXESB/Logger}}"
                    /* Logger XSLT:
                       ESBUUID         = OMXTrackingId  [if exists]

                    */));

                isSkipped = false;
            }

            if (!isSkipped) {
                orderCurrentActivity.Status =
                    RuleFunctions.Helpers.GetActivityStatusString("1", false);  // IN_PROGRESS
                RuleFunctions.Helpers.SendDataToDB(orderRequest);
            } else {
                RuleFunctions.Helpers.SkipActivity(orderRequest, orderCurrentActivity, "4");
            }

        } catch (Exception ae) {
            RuleFunctions.Helpers.HandleActivityException(
                orderRequest, orderCurrentActivity, ae, "");
        }
    }
