Request_CCBS_OFFER_POOLING_POOLED

Backend: CCBS / CES (GoldenDB routing) Pattern: Fire-and-Forget Author: SathidP-PC Generated: 2026-09-23
§1 — Overview & Purpose

Collects poolable SOC codes from the order's Agreement Offers (filtered by SPECIAL_OFFER_INDICATOR = "RPD" or "CPD") and RelatedOffers, then submits a single pooling request to CCBS (standard) or CES (when OrderData.GoldenDB = "Y"). The activity enables the bundled billing plan to be correctly pooled across parent and child OUs. If no eligible SOCs are found, no request is sent and the activity is skipped.

§4 — Rule Conditions (WHEN)
  1. orderCurrentActivity@extId == orderRequest.ProcessFlow.NextActivityName
  2. orderCurrentActivity.ActivityID == "CCBS_OFFER_POOLING_POOLED"
  3. orderRequest.ProcessFlow.NextActivityID == "CCBS_OFFER_POOLING_POOLED"
  4. orderCurrentActivity.Status == "WAITING"
§5 — Execution Flow
  1. Read GoldenDB flag from OrderData.GoldenDB
  2. Collect SOC IDs from POU/ChildOU Agreement Offers where SPECIAL_OFFER_INDICATOR == "RPD" or "CPD"
  3. Append SOC IDs from RelatedOffers (unconditionally)
  4. Guard: if socIDs@length == 0 → SkipActivity; else proceed
  5. Determine event type: GoldenDB == "Y" → CES_OFFER_POOLING_POOLED (with CES extId); else → CCBS_OFFER_POOLING_POOLED
  6. Build ns:OfferPoolingPooledRequest with one <SOCCode> per item in socIDs
  7. Event.Ext.sendEventImmediate(reqEvent); RequestCount++
  8. Set activity to IN_PROGRESS; send audit log event

§19 — Response Message Rule

§19.1 Overview

Parses CCBS_OFFER_POOLING_POOLED response into a CCBS_OfferPoolingpooledRes concept. Extracts pooled SOC mappings from the response payload. Returns "true" unconditionally (no RequestCount fan-in check).

§19.4 Fan-in Completion

Response handler returns "true" unconditionally — there is no RequestCount == successResponseCount check. The single pooling request is sent once; the activity advances on the first (and only) response.
