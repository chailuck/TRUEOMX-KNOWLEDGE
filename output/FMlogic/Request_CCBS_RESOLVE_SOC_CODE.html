Request_CCBS_RESOLVE_SOC_CODE

CCBS Offer Name → SOC Code Resolution with GoldenDB Dual-Path Dispatch
Priority: 5 forwardChain: true Backend: CCBS / CES (GoldenDB) Channel: OMXFMConnectionRequest Author: mmittal--t420 Generated: 2026-07-27
§1 — Overview & Purpose

This rule fires when the order reaches ActivityID = CCBS_RESOLVE_SOC_CODE and status WAITING. It resolves offer names to SOC codes for any offer that has an OfferName set but a blank Soc field — across Agreement offers, SubscriberOffers, and their RelatedOffersArrays at all hierarchy levels.

Key distinction from CCBS_GOD: CCBS_GOD collects SOC codes (already known) to fetch product catalog details. CCBS_RESOLVE_SOC_CODE collects offer names where the code is still unknown and asks CCBS to return the matching SOC code. This step must run after CCBS_GOD has populated SocProperties to allow the NextPricePlan lookup.
Dual dispatch path — GoldenDB gate:
  • Path A (GoldenDB=Y): Sends CES_RESOLVE_SOC_CODE event — routes to CES/GoldenDB service. The event element carries an extId attribute generated by OMXUtils:generateTrackingID().
  • Path B (standard): Sends CCBS_RESOLVE_SOC_CODE event — routes to CCBS. No extId attribute on event element.
Both paths use the same payload: ns:ResolveSocCodeRequest with N × ns:SocName. RequestCount is incremented once regardless of path.
⚠ Resubmission awareness: Before adding an offer to the batch, the rule checks orderCurrentActivity.Response[] for an existing entry with matching ReferenceId and CompletionStatus==2. If found, the offer is skipped (already resolved in a prior attempt). Agreement-level offers additionally short-circuit via a direct Response@length == 0 check before the per-response loop.

§17 — Migration Notes & Recommendations

Functional Requirements

  • R1 — Collect all offer names where OfferName ≠ blank AND SocCode = blank, across Agreement, SubscriberOffers, RelatedOffers at all hierarchy levels.
  • R2 — Run per-offer PreExecCheck including for related offers (new helpers with 4th parameter).
  • R3 — Check resubmission guard: skip offers already in Response[].ReferenceId with CompletionStatus=2.
  • R4 — Also include offer names for "next price plan" entries from SocProperties where GOD hasn't returned a code.
  • R5 — Dispatch to CES (if GoldenDB=Y) or CCBS (standard). CES request includes event-level extId attribute.
  • R6 — Single batch dispatch; RequestCount always = 1.
  • R7 — Response: for each ResolveSocCode[m], find matching offers by OfferName == SocName and write Soc = SocCode.
  • R8 — Response: also inject ServiceType from Parameter["SERVICE_TYPE"] to matching subscriber offers and related offers.
  • R9 — Fan-in: RequestCount == Response@length — always 1:1.

§19 — Response Message Rule

§19.1 — Overview

RuleFunctions.OrderResponse.Response_CCBS_RESOLVE_SOC_CODE receives the CCBS/CES response and:

  1. Creates CCBSResolveSocCodeRes concept with base response fields + a ResolveSocCode[] array
  2. Looks up SERVICE_TYPE from currActivity.Parameter
  3. For each resolved pair (SocName → SocCode), scans ALL offer positions and writes Soc and optionally ServiceType
  4. Sends response audit log
  5. Returns "true" when RequestCount == Response@length
