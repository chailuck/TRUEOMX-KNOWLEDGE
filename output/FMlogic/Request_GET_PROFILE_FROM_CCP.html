Request_GET_PROFILE_FROM_CCP

FM Logic Documentation — CCP User Profile Query & Dynamic SubscriberOffers Enrichment (Data Pipeline for CCP_REMOVE_OFFER)
Rule: Rules.OMConsumers.OMXFM.Request.Request_GET_PROFILE_FROM_CCP Priority: 5 Backend: CCP (queryUserProfile → GetPrepaidCreditInfoRequest) Pattern: Parallel per-Subscriber dispatch Generated: 2026-09-11
§1 — Overview & Purpose

GET_PROFILE_FROM_CCP queries CCP for each subscriber's current price plan profile, then enriches the order working memory by dynamically appending new SubscriberOffers entries for any active grading-type price plans found. These dynamically-added offers are then consumed by the subsequent CCP_REMOVE_OFFER activity — making this FM a data pipeline step, not just a lookup.

The response RF filters CCP's PricePlanDtoList for plans with names starting with IPP_000O0_00_GRADING. For each such plan found, it creates a SubscriberOffers concept (Action=Remove, FE_OR_CCBS=CCP) and appends it to the subscriber — effectively "staging" the grading offers for removal in the next activity.

Schema / Name mismatch: Despite the FM name saying GET_PROFILE_FROM_CCP, the request payload schema is ns:GetPrepaidCreditInfoRequest and CCP's response is queryUserProfileResponse. Debug comments in both files reference the old name CCP_GET_PREPAID_CREDIT_INFO. The FM was renamed without updating the payload schema namespaces. Functionally correct.

§7 — Data Extraction & Pre-Processing

§7.1 — Idempotency Check (per Subscriber)

Checks Response[iResp].ReferenceId == refId && CompletionStatus == 2. If found, subscriber is skipped (reqSuccess = true). Key: refId = subscriber's RefId (not an offerRefId — per subscriber, not per offer).

§7.2 — PreExecCheck (dynamic from Activity)

The PreExecCheck XPath expression is read from nextAct.PreExecCheck (i.e., from the ProcessConfig activity definition), not hardcoded in this rule. The helper GetXMLForSubscriber (ParentOU) or GetXMLForSubscriberInChildOU (ChildOU) builds the XML fragment that is fed to XPath.execute. If the PreExecCheck field is empty, all subscribers pass.

§7.3 — XSLT Param Design: Index vs. Value

Unlike most other FMs that pass extracted string values (e.g., $msisdn, $refId), this FM passes the subscriber's array indices ($i, $j, $p, $q) as XSLT parameters. The XSLT then navigates using ParentOU[$i+1]/Subscriber[$j+1] (1-indexed XPath from 0-indexed BE vars). This avoids extracting values in the BE layer but ties the XSLT tightly to the concept array structure.

§7.4 — Response: PricePlanDtoList Parsing

The response RF reads $eventResponse/payload/xsd2:queryUserProfileResponse/xsd2:queryUserProfileReturn/xsd2:PricePlanDtoList/xsd2:PricePlanDto (namespace xsd2=http://thaitrue.customization.ws.bss.zsmart.ztesoft.com). For each plan, it reads xsd2:PricePlanName and tests:

if (String.startsWith(pp_name, "IPP_000O0_00_GRADING"))

This filters for grading-tier plans specifically. Only these plans result in a new SubscriberOffers concept being added.

§7.5 — Response: Subscriber Concept Lookup

The response RF resolves the Subscriber concept from working memory by extId:

  1. Try "SUB:" + OMXTrackingId + ":" + RefID (ParentOU subscriber extId format)
  2. If null, try "CSUB:" + OMXTrackingId + ":" + RefID (ChildOU subscriber extId format)

This dual-lookup pattern allows the same response handler to work for both ParentOU and ChildOU subscribers regardless of which sent the request.

§7.6 — Response: Dynamic SubscriberOffers Creation

For each matched grading plan, a new Concepts.OrderRequest.OrderElements.SubscriberOffers concept is created with:

FieldValue
@extIdOMXUtils:generateTrackingID()
OfferName$pp_name (the PricePlanName from CCP)
Action"Remove" (static)
ExtendedInfo/@extIdOMXUtils:generateTrackingID()
ExtendedInfo/Name"FE_OR_CCBS" (static)
ExtendedInfo/Value"CCP" (static)

This concept is appended to subscriber.SubscriberOffers[]. The FE_OR_CCBS=CCP flag will be read by CCP_REMOVE_OFFER's PreExecCheck to identify these as CCP-routed removal targets.

The PREPAID_REMOVE_PACKAGE flow uses this to discover which CCP grading offers need removal before calling CCP_REMOVE_OFFER.

§13 — Exception / Error Handling

Request rule: Standard catch(Exception ae) → HandleActivityException.

Response RF: No try/catch — response processing (subscriber lookup, PricePlanDto iteration, concept creation) runs without exception handling. A ZSMART response parsing failure would propagate uncaught.

The response RF's PricePlanDto parsing loop and SubscriberOffers creation have no try/catch. If CCP returns a malformed response or the subscriber concept is null, the exception would propagate uncaught to the BE rule engine.

§19.1 — Overview

The response RF does significantly more than just record the response — it is a data enrichment step. It: (1) records the standard ResponseBase, (2) looks up the Subscriber concept, (3) parses CCP's PricePlanDtoList to find grading plans, and (4) dynamically creates SubscriberOffers concepts for CCP_REMOVE_OFFER to consume.
