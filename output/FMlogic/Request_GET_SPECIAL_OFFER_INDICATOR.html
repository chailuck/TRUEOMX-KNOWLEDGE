Request_GET_SPECIAL_OFFER_INDICATOR

SOC Property Batch Lookup — Collect All SOC Codes then Query in a Single Call
Priority: 5 forwardChain: true Author: smandal-t410 Pattern: Single Batch Request Routing: GoldenDB Fork Generated: 2026-07-27
§1 — Overview & Purpose

This rule retrieves SOC property indicators (primarily TR_SPECIAL_OFFER_IND) from a backend service for every offer in the order. It uses a fundamentally different dispatch pattern from the IntraActivitySequencing FMs: it first collects all unique SOC codes across the entire order (all subscribers, agreement offers, and their related offers, ParentOU + ChildOU), then sends a single batch request containing all those SOC codes in one call.

Different dispatch pattern: This FM does NOT use IntraActivitySequencing. It sends one Event.Ext.sendEventImmediate(reqEvent) with all SOCs batched into a single GetSpecialOfferIndicatorRequest, increments RequestCount once, and always receives a single response.
GoldenDB routing fork: If orderRequest.OrderData.GoldenDB == "Y", the request is sent via a CES-based channel (CES_GET_SPECIAL_OFFER_INDICATOR event) with an extId in the event. Otherwise, the standard Amdocs RM3G-based channel is used.
Two activity parameters control runtime behavior:
  • ADD_PROP — comma-separated list of additional SOC property names to retrieve alongside TR_SPECIAL_OFFER_IND
  • CHECK_LOYALTY_SOC=Y — triggers loyalty SOC detection: if the returned TR_SPECIAL_OFFER_IND value starts with "LY", creates additional LOYALTY and OLD_LOYALTY_SOC ExtendedInfo on that offer

§9 — Request Payload Build

§9.1 — SOC Collection Logic (pre-payload)

// Unique SOC list collection (order-wide, all offer containers) Object alSOCs = Collections.List.createArrayList(); // 4 scan loops — same guard on each: // "count(offer/ExtendedInfo[Name='SPECIAL_OFFER_INDICATOR']) = 0" // Scan ParentOU → Subscriber[j].SubscriberOffers[k] for(i, j, k) { if(!SPECIAL_OFFER_INDICATOR already in offer) alSOCs.add(SubscriberOffers[k].Soc) for(l) alSOCs.add(RelatedOffersArray[l].Soc) // no guard on related } // Scan ParentOU → Agreement.Offers[j] for(i, j) { if(!SPECIAL_OFFER_INDICATOR already in offer) alSOCs.add(Agreement.Offers[j].Soc) for(k) alSOCs.add(RelatedOffersArray[k].Soc) } // Scan ParentOU → ChildOU[p] → Subscriber[q].SubscriberOffers[r] for(i, p, q, r) { if(!SPECIAL_OFFER_INDICATOR already in offer) alSOCs.add(SubscriberOffers[r].Soc) for(s) alSOCs.add(RelatedOffersArray[s].Soc) } // Scan ParentOU → ChildOU[p] → Agreement.Offers[q] for(i, p, q) { if(!SPECIAL_OFFER_INDICATOR already in offer) alSOCs.add(Agreement.Offers[q].Soc) for(r) alSOCs.add(RelatedOffersArray[r].Soc) } Object[] socStrings = Collections.toArray(alSOCs);

The same payload structure applies to both GoldenDB and standard paths — only the event type, root element namespace, and extId presence differ.

§17 — Migration Notes & Recommendations

Functional Requirements

  • R1 — This is a cross-entity batch FM: one request for all SOC codes across ALL subscribers, agreements, ParentOU, and ChildOU. Migration must preserve the pre-aggregation and deduplication step before the API call.
  • R2 — The SPECIAL_OFFER_INDICATOR guard (skip offers already enriched) must be preserved in the collection phase AND in the response write-back phase — both check independently.
  • R3 — GoldenDB=Y routes to a different backend channel. Migration should externalize this routing as a configurable strategy, not hard-coded.
  • R4 — ADD_PROP parameter: additional property names beyond TR_SPECIAL_OFFER_IND are requested dynamically. The response write-back loop handles all returned properties generically.
  • R5 — CHECK_LOYALTY_SOC=Y: if set, the LY-prefix detection logic adds two additional ExtendedInfo entries per qualifying offer (LOYALTY value + OLD_LOYALTY_SOC=Y marker). The OLD_LOYALTY_SOC flag is only set when the subscriber already has an FE offer with TR_SPECIAL_OFFER_IND=LY in SocProperties.
  • R6 — Fan-in is trivially "always true": single request → single response → return "true" immediately. No count tracking needed.
  • R7 — Response write-back covers 4 distinct offer containers (ParentOU.Agreement, ParentOU.Subscriber, ChildOU.Agreement, ChildOU.Subscriber) — all must be covered by migration.

§19 — Response Message Rule

§19.1 — Overview

The response rulefunction creates a GetSpecialOfferIndicatorRes concept and then iterates all offer containers (ParentOU Agreement, ParentOU Subscriber, ChildOU Agreement, ChildOU Subscriber) to write SPECIAL_OFFER_INDICATOR and additional property ExtendedInfo back onto each qualifying offer. Finally it returns "true" unconditionally (no fan-in counting required — single batch request/response).

§19.4 — Loyalty SOC Detection Logic

// Fires when CHECK_LOYALTY_SOC activity param == "Y" AND SPECIAL_OFFER_INDICATOR value starts with "LY" // Applies to ParentOU and ChildOU SubscriberOffers if(chkLoyaltySocParam == "Y" && specialOfferIndExtInfo.Value.startsWith("LY")) { // Check: does this subscriber already have a FE offer with TR_SPECIAL_OFFER_IND=LY in SocProperties? boolean oldLoyaltySoc = exists(Subscriber.SubscriberOffers[ ExtendedInfo[Name="FE_OR_CCBS" AND Value="FE"] AND contains(SocProperties, "TR_SPECIAL_OFFER_IND=LY") ]); if(oldLoyaltySoc) { // Mark that an old loyalty SOC exists on this offer curOffer.ExtendedInfo[n] = {Name="OLD_LOYALTY_SOC", Value="Y"}; } // Always add the LOYALTY tier value (part after "LY" prefix) curOffer.ExtendedInfo[n+1] = {Name="LOYALTY", Value=substring-after(specialOfferIndExtInfo.Value, "LY")}; }
