§1 — Overview & Purpose

Submits a child order to the OMX SubmitOrder service for each subscriber, carrying loyalty offers (filtered by TR_SPECIAL_OFFER_IND=LY). Unlike FM calls that target external backends, this FM creates an internal OMX child order using the OMX_CREATE_CHILD_ORDER event. The ORDER_TYPE and SBM channel are configurable via activity parameter and global variable. A monotonic childIndex counter is used to construct unique child order IDs across POU and COU subscribers.

9.2 childIndex & orderId

childIndex starts at 0, increments BEFORE the resub guard check. The child order ID is constructed as:

ns:orderId = concat(OrderID, "-", childIndex)

Example: main order ORD-123 → child orders ORD-123-1, ORD-123-2, etc.

9.3 Offer Filtering Logic (per subscriber)

BlockConditionOffers Included
Primary (always)FE_OR_CCBS="FE" AND SocProperties contains "TR_SPECIAL_OFFER_IND=LY"FE loyalty offers — expirationDate, offerName, serviceType, soc
Secondary (gated)exists(SubscriberOffers[FE_OR_CCBS="CCBS" AND SocProperties contains "TR_SPECIAL_OFFER_IND=LY"]) → then loop FE ServiceType=86 & OfferRate>0FE paid data offers when CCBS loyalty offers exist; expirationDate only when RevenueType="OC"

RefRequirement

R2childIndex = monotonic counter starting at 0, shared across POU and COU. Increments before resub guard.
R3orderId = concat(OrderID, "-", childIndex). Unique child order ID per subscriber per original run.

§19 — Response Message Rule (Response_OMX_SUBMIT_POSTPAID_ADD_BENEFIT)

Uses the dedicated Concepts.FM.Response.OMX_CreateChildOrder concept (not ResponseBase). Captures an additional childOmxTrackingId field from the SubmitOrder response payload — allowing the main order to track the child order tracking ID for downstream correlation.
