Request_OMX_EXP_FUT_BALOS

Expire future orders from a prior OMX_SEARCH_FUT result — dual usage: FULLSUS/FCVG/CCVG expiry (step 36) and CANCEL expiry (step 38, EXT=_CANCEL)

Priority: 5 ForwardChain: true Target: OMX (internal) Event: OMX_UPDATE_FUTURE Fan-in: hardcoded "true" Used in RESTORE: Steps 36, 38
§1 — Overview & Purpose

This FM reads the results of a prior OMX_SEARCH_FUT activity from the ProcessFlow working memory and sets matching future orders to status=4 (expired). It is called twice in RESTORE:

  • Step 36 (no EXT param): reads from activity extId PROCESS:OMX_SEARCH_FUT; expires FULLSUS future orders with ActivityReason=SUS1 or FCVG, and CANSUB orders with ActivityReason=CCVG.
  • Step 38 (EXT=_CANCEL param): reads from activity extId PROCESS:OMX_SEARCH_FUT_CANCEL; type set to "CANCEL"; same filter criteria.

Fan-in: hardcoded "true" — The response rulefunction always returns "true" regardless of ResponseCode. There is no per-subscriber loop and no RequestCount check. Any failure from OMX_UPDATE_FUTURE is silently accepted.

Logger OPERATION_NAME: Both request and response loggers use "OMX_EXP_FUT" — not "OMX_EXP_FUT_BALOS".

1
Evaluate PreExecCheck on serialised orderRequest (order-level, not subscriber-level)
2

3

4

5

6

7
If isSkipped → SkipActivity("4"); else status=PROCESSING + SendDataToDB

§17 — Migration Notes & Recommendations

§19 — Response Rule: Response_OMX_EXP_FUT_BALOS

Maps response to OMX_UpdateFutureRes concept (no ReferenceId — order-level response), appends to currActivity.Response[], sends audit log, then always returns "true".

§19.4 Fan-in / Completion Logic

[HIGH RISK] Response rulefunction always returns "true" — there is no ResponseCode check. Even if OMX returns an error, the process advances. This is by design (non-blocking cleanup step) but creates a silent failure risk.
