Request_SMDP_PLUS

TIBCO BusinessEvents FM Logic — SM-DP+ eSIM Profile Download (Per-Offer Parallel Fan-out)
Author: SathidP-PC Priority: 5 Forward Chain: true Target: SM-DP+ (eSIM Profile Server) Pattern: Per-Offer Fan-out — Two XSLT Variants Lines: 238 + 42
§1 — Overview & Purpose

This rule initiates eSIM profile download by dispatching DownloadOrderRequest events to SM-DP+ (the eSIM Profile Server). It processes subscriber offers at the offer level — filtering to eSIM offers (serviceType="80") by default — and dispatches one or more SMDP_PLUS_DOWNLOAD JMS events depending on the PROJ parameter and offer configuration.

Two distinct dispatch branches: Branch A (PROJ=RIO_SWAP or PROJ=ESIM) dispatches one event per subscriber and then breaks the offer loop. Branch B (standard) iterates all qualifying offers, sending one event per offer. The ICCID, EID, and VENDOR field sources differ significantly between branches. Parameters with value "BLANK" suppress the corresponding payload element entirely (Branch B only).
Fan-in difference from all other FMs: Success check uses tib:right(tib:trim(ResponseCode), 2) = "00" (last 2 chars) rather than the standard "000" (3 chars) used elsewhere in this process.

§4 — eSIM Offer Pre-Filter

This FM iterates at the offer level (SubscriberOffers), not the subscriber level. Before dispatching, each offer is evaluated against:

if ((serviceType == null || serviceType == "80") AND (orderValue != "RESUME" AND paramValue != "ESIM")) → continue (skip offer)

In plain terms: skip offers that are NOT eSIM type (80) — unless the order is in RESUME mode or PROJ=ESIM. This makes SMDP_PLUS an eSIM-exclusive FM in normal execution.

Additionally, ExtendedInfo[Name="FE_OR_CCBS"]/Value from the offer is read as a filter flag and passed to the PreExecCheck XML helper, which determines whether the offer qualifies for further processing.

§5.1 Branch A — RIO_SWAP / ESIM Logic

Additional gate inside Branch A: count(subscriber.ResourceInfo[ResourceName="OLD_EID" and Source="FE"]) > 0 OR paramValue="ESIM"

If this secondary gate fails → skip to Branch B handling (else branch = Branch B logic).

EID working memory mutation (before dispatch): If subscriber has no EID resource and NEW_EID resource exists → create EID ResourceInfo with Source="FE" and append to subscriber.

Potential bug in COU Branch A (line 174): The EID lookup reads $subscriberPou/ResourceInfo[ResourceName='NEW_EID'] inside the COU loop where the correct variable is $subscriber (the COU subscriber), not $subscriberPou (the outer POU variable). This means COU Branch A incorrectly reads the parent OU subscriber's NEW_EID instead of the child OU subscriber's own NEW_EID. The POU path (line 98) correctly uses $subscriberPou.

§5.2 Branch B — Standard Logic

  • No OLD_EID gate — all qualifying eSIM offers proceed
  • No EID working memory mutation
  • "BLANK" suppression for all three fields: if parameter value is "BLANK" → omit the element from payload
  • VENDOR and ICCID sourced from offer level (currSubOffer.ExtendedInfo) not subscriber level
  • No break — all offers are processed

§8 — Working Memory Mutation (Branch A Only)

In Branch A (RIO_SWAP/ESIM), before dispatching the JMS event, the rule may create a new EID ResourceInfo and append it to the subscriber's working memory:

GateActionextId
No existing EID resource on subscriber AND NEW_EID value not blankCreate ResourceInfo{ResourceName="EID", ValuesArray=$eid, Source="FE"}concat(subscriber/@extId, "EID", $eid)

This ensures the EID is available in working memory for subsequent activities even if it was not part of the original FE input.

COU Bug (line 174): In the COU loop, the EID value is read from $subscriberPou/ResourceInfo[ResourceName='NEW_EID'] (the outer POU variable) but should be $subscriber/ResourceInfo[ResourceName='NEW_EID'] (the COU subscriber). This causes the COU subscriber to inherit the POU subscriber's NEW_EID instead of its own.
§9 — Execution Flow
  1. Read all parameters: ICCID, EID, VENDOR, PROJ (×2), ORDER
  2. Read LogicalDate concept (dead — variable set but not used in payload)
  3. Initialize dead variables: requestedDate, requestedBy, requestedByUser, futureType (never used)
  4. Loop POU Subscribers → Loop POU Subscriber Offers:
    1. ServiceType + ORDER/PROJ pre-filter (skip non-eSIM unless RESUME/ESIM)
    2. Read FE_OR_CCBS filter from offer
    3. Execute PreExecCheck if present
    4. reqSuccess check: Response[ReferenceId == SubscriberId (not RefId!) AND CompletionStatus==2]
    5. If PROJ=RIO_SWAP or ESIM → Branch A (§5.1): OLD_EID/ESIM gate → EID mutation → send event → break
    6. Else → Branch B (§5.2): send offer-level event (no break)
  5. Loop COU Subscribers (same offer-level logic)
  6. If !isSkipped: GetActivityStatusString("1", false) + SendDataToDB()
  7. Else: SkipActivity("4")
  8. catch: custom status resets + HandleActivityException()
reqSuccess uses SubscriberId, not RefId: Response[ReferenceId == subscriberPou.SubscriberId] (not subscriberPou.RefId). This is unusual — most FMs match by RefId. The RefID in the outbound event payload is set to $subRefId (= subscriber.RefId) but the response match is by SubscriberId.

§17 — Migration Notes & Recommendations

Functional Requirements

  • R1 — Only process eSIM offers (serviceType="80") unless ORDER=RESUME or PROJ=ESIM
  • R2 — PROJ=RIO_SWAP/ESIM: one event per subscriber (break after first), subscriber-level ICCID/EID/VENDOR sources
  • R3 — Standard PROJ: one event per qualifying offer, offer-level ICCID/VENDOR sources
  • R4 — "BLANK" parameter value suppresses the corresponding payload element (Branch B only)
  • R5 — EID precedence: param → PEID(FE, not NONE-) → NEW_PEID (Branch A) / EID(FE) (Branch B)
  • R6 — ICCID fallback uses ICC_ID_CHG_SUM+"F" suffix (Luhn checksum result from prior step)
  • R7 — Fan-in: last 2 chars "00" check (NOT 3-char "000" as in other FMs)
  • R8 — Credentials (UserName/PassWord) are included in every SMDP_PLUS_DOWNLOAD payload
  • R9 — EID working memory mutation (Branch A): create EID ResourceInfo from NEW_EID if absent
