Request_OMX_NOTI_TO_KAFKA

Publishes a complete order-status notification to Kafka — a single request per invocation serializing the full OrderRequest snapshot into ns5:orderStatusNotification. Used at two points in the Knox device flow (step 66: Knox event, step 69: Knox notify) with different ProcessConfig Parameter keys.
Backend: Kafka (Order Status Notification) Pattern: Single request (not per-offer) forwardChain: true Used in steps: 66, 69 Generated: 2026-08-07
§1 — Overview & Purpose

Publishes one Kafka order-status notification per invocation. Unlike most OMXFM rules this is not a per-offer fan-out — it fires once, serializes the complete OrderRequest, and sends it as a single ns5:orderStatusNotification message. The same FM is reused at two workflow steps (66 and 69) with different Parameter[1] values that control the Kafka message header key/value (allowing routing to different Kafka topics or consumers).

  • Pattern: Single request — no SubscriberOffer loop; whole OrderRequest serialized
  • PreExecCheck context: Instance.serializeUsingDefaults(orderRequest) — full serialization
  • Parameter dispatch: Parameter[1] parsed as key=value → headerName/value in event headers
  • Payload: ns5:orderStatusNotification — 250+ fields covering Order, Customer, Account, Subscriber, Agreement, Product, contacts, billing, service, resource, MNP, and extended info
  • Response audit log: OPERATION_NAME dynamically derived from step extId (different per step)
  • Debug traces: System.debugOut("Response OMX_NOTI_TO_KAFKA : 001–005") left in production rulefunction
  • Dead code: Commented-out second Event.createEvent on line 39 (replaced by active version)
[LOW] System.debugOut traces in production: The response rulefunction contains 5 debug trace statements. These have no functional impact but add noise to logs and indicate the file was not cleaned after development.
[LOW] Dead code — commented-out Event.createEvent: Line 39 contains a commented-out alternative XSLT for the Kafka event. It is not executed but inflates the file to 656KB. Should be removed.
Step reuse pattern: The same FM at step 66 (OMX_NOTIFY_KNOX_EVENT) and step 69 (OMX_NOTIFY_KNOX_EVENT_NOTIFY) sends different notifications by varying the ProcessConfig Parameter[1] key=value. The audit log OPERATION_NAME is derived dynamically from the step's extId, so each invocation logs its step identity correctly.

§4 — Parameter Dispatch (ProcessConfig Parameter[1])

The first activity Parameter is parsed as a key=value string and mapped to JMS event headers:

VariableXPathMaps to
param$orderCurrentActivity/Parameter[1]Raw key=value string from ProcessConfig
paramKeytib:tokenize($param, "=")[1]headerName in event — Kafka routing key
paramValuetib:tokenize($param, "=")[2]value in event — Kafka routing value
Step 66 (OMX_NOTIFY_KNOX_EVENT) and step 69 (OMX_NOTIFY_KNOX_EVENT_NOTIFY) each have a different Parameter[1] in the ProcessConfig XML, allowing the same FM to publish to different Kafka header destinations. The actual Kafka topic is routed externally by the ESB based on these headers.

§17 — Migration Notes & Recommendations

Functional Requirements

RefRequirement
R1Single Kafka notification per invocation (not per offer). Full OrderRequest snapshot sent.
R2ProcessConfig Parameter[1] parsed as key=value; key → headerName, value → value in event. Controls Kafka routing.
R3PreExecCheck evaluated against Instance.serializeUsingDefaults(orderRequest) — full OrderRequest context.
R4Payload: ns5:orderStatusNotification (ns5=http://services.omx.truecorp.co.th/OrderStatus) containing 250+ fields from OrderRequest.
R5Response audit OPERATION_NAME is dynamic: tib:substring-after-last(currActivity@extId, ":") — different per step invocation.
R6Fan-in: RequestCount == successResponseCount (suffix "000"). Always 1 request, so fan-in completes on first response.
