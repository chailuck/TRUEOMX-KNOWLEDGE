Request_OMX_CAL_CREDIT_LIMIT_FOR_IR

Calculates and updates IR (International Roaming) credit limit per Account — two backend variants (CES/GoldenDB or standard OMX FM); response applies a 3-way credit limit business rule using the IRCreditLimit/CreditGroupAmount global variable, then writes IS_CHANGE_CREDIT_LIMIT to Account.ExtendedInfo.
Backend: OMX FM or CES (GoldenDB gate) Pattern: Per-Account fan-out forwardChain: true Author: RS33-BANDIT Used in step: 47 Generated: 2026-08-06
§1 Overview & Purpose

Fetches the IR credit limit from the backend (OMX FM or CES based on GoldenDB flag), then applies a business rule to calculate the new PersonalCreditLimit for each Account using a tier table loaded from a global variable. Writes IS_CHANGE_CREDIT_LIMIT (Y/N) to Account.ExtendedInfo to signal downstream steps whether a credit limit change is required.

  • Traverses Account[] (not Subscriber[]) — per-account fan-out
  • Per-account resub guard: skips accounts where CompletionStatus==2 && ReferenceId==refId already in Response[]
  • GoldenDB gate selects event type: CES_CAL_CREDIT_LIMIT vs OMX_CAL_CREDIT_LIMIT_FOR_IR
  • Fan-in: RequestCount == Response@length
  • SendDataToDB called once after the request loop
Response audit unconditional: Unlike the request audit (gated by AllowWriteLog), the response audit logger fires for every order type.

§6 Response — IR Credit Limit 3-Way Calculation

After creating the response concept, the handler looks up the account by extId pattern "A:" + OMXTrackingId + ":" + RefID and applies the IR credit limit business rule:

Step 1 — CreditGroupAmount Global Variable Lookup

Global variable: OMX_OM/BizRules/IRCreditLimit/CreditGroupAmount

Default value (pipe-delimited):

,A,B,D,E,X,=3000:10000|,C,S,W,=1000:4000|,GA,GB,GC,GD,GE,=3000:10000| ,LA,LB,LC,LD,LE,=3000:10000|,MA,MB,MC,MD,ME,=3000:10000| ,NA,NB,NC,ND,NE,=3000:10000|,RA,RB,RC,RD,RE,=3000:10000

Format per entry: <,class1,class2,...,>=<incAmount>:<maxAmount>

Match: String.contains(group, "," + CreditClass + ",") — first matching group wins (break on match)

Step 2 — Base Credit Limit

creditLimit = max(acct.AccountManagementInfo.PersonalCreditLimit, activityRes.CreditLimit)

Takes the higher of the existing personal limit and the backend-returned credit limit.

Step 3 — 3-Way Update Rule

CaseConditionAction on PersonalCreditLimitIS_CHANGE_CREDIT_LIMIT
1 — At/above max maxAmt <= creditLimit Set to creditLimit (no increase) N
2 — Increment hits cap maxAmt <= creditLimit + incAmt Set to maxAmt (capped) Y *
3 — Room to increment else Set to creditLimit + incAmt Y
Dead branch in Case 2: The inner if(maxAmt == creditLimit) check inside Case 2 → IS_CHANGE=N can never be true. Case 2 only fires when Case 1 (maxAmt <= creditLimit) is false — meaning maxAmt > creditLimit. Thus maxAmt == creditLimit is impossible in Case 2. The IS_CHANGE=N branch inside Case 2 is dead code.

Step 4 — IS_CHANGE_CREDIT_LIMIT Write

If not(exists(acct/ExtendedInfo[Name="IS_CHANGE_CREDIT_LIMIT"])) → append AccountExtendedInfo{Name="IS_CHANGE_CREDIT_LIMIT", Value="Y"/"N"} to acct.ExtendedInfo[]. Idempotent — won't write a second time if already present.

§9 Migration Notes & Recommendations

Functional Requirements

RefRequirement
R1Per-account fan-out (not per-subscriber). Loops Account[].
R2GoldenDB gate: OrderData.GoldenDB == "Y" → CES backend with @extId + CES header; else OMX FM backend.
R3Per-account resub guard: skip accounts where Response[].CompletionStatus==2 && ReferenceId==refId.
R4Credit limit rule: load IRCreditLimit/CreditGroupAmount global variable (default fallback included in BE source). Find group by CreditClass. Take creditLimit = max(PersonalCreditLimit, CES/OMX CreditLimit). Apply 3-way capping rule.
R5Write IS_CHANGE_CREDIT_LIMIT to Account.ExtendedInfo only if not already present (idempotent XPath check).
R6Account lookup in response: Instance.getByExtIdByUri("A:" + OMXTrackingId + ":" + RefID) — extId must follow this exact pattern.
R7SendDataToDB called once after the full account loop — not per-account.
