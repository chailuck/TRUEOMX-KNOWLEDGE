Request_CCBS_ESIM_SWAP_SIM

Execute eSIM swap in CCBS via mSimData API; pre-populates PEID/PMATCHID ResourceInfo with Source=FE; sets IS_CALLED_MSIM_SWAP_SIM=Y — CRITICAL: response always returns "true" without checking fan-in count
Rule Priority: 5 ForwardChain: true Backend: CCBS (eSIM) Pattern: Fire-and-Forget Author: sakarin-radchapunya
⛔ Critical Migration Risk: The response rulefunction for CCBS_ESIM_SWAP_SIM always returns "true" unconditionally. There is NO fan-in count check — successResponseCount is never calculated. The engine declares completion after the first response regardless of how many requests were sent. This may cause partially-processed bulk eSIM swaps to appear complete. Target architecture must implement proper fan-in.
§1 — Overview & Purpose

This rule fires when the process reaches CCBS_ESIM_SWAP_SIM (steps 27 and 28 in SWAPSIM). It performs the eSIM swap call to CCBS via the same mSimData/OUList schema as CCBS_MSIM_SWAP_SIM but uses the eSIM endpoint and handles eSIM-specific resource types (PEID, PMATCHID). Before building the request, it pre-populates missing PEID ResourceInfo (from NEW_PEID, Source='FE') and PMATCHID ResourceInfo (from NEW_PMATCHID, Source='FE') on the subscriber. In the XSLT payload, NEW_PEID and OLD_PEID values are packed with subscriberId: concat(ValuesArray, '_', $subscriber/SubscriberId). The pattern is fire-and-forget (sendEventImmediate + RequestCount++). As a side effect, IS_CALLED_MSIM_SWAP_SIM=Y is set on subscriber.ExtendedInfo to gate downstream steps 34 (CCBS_SWAP_SIM_POSTPAID_SUB).

Steps 27 and 28 both use ActivityID CCBS_ESIM_SWAP_SIM with different PreExecCheck conditions: step 27 handles non-bulk (no FILE_ID), step 28 handles bulk (FILE_ID exists).

§19 — Response Message Rule
⛔ Critical Defect: The response rulefunction returns "true" unconditionally without any fan-in logic. The successResponseCount XPath is completely absent — not even commented out. This means after ANY single CCBS eSIM response arrives, the activity is considered complete regardless of RequestCount. For bulk eSIM operations (step 28) this is a correctness bug.
