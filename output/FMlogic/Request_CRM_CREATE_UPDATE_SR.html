FM Logic Documentation

Request_CRM_CREATE_UPDATE_SR

Create or update a Service Request in CRM — fire-and-forget pattern with dual POU+COU loop
Backend: CRM Pattern: POU+COU Loop · Fire-and-Forget Author: CHAYATORN-PC Priority: 5 Generated: 2026-09-18
§1 — Overview & Purpose

This rule creates or updates a Service Request (SR) in the CRM system for each subscriber (POU and COU). It uses a fire-and-forget pattern — unlike most FM rules it does not use IntraActivitySequencing. Instead it uses Event.Ext.sendEventImmediate directly and manually increments RequestCount++.

The payload varies by OrderType: OrderType 1 or 11013 is a Call Verification flow that maps CALL_VER_* ExtendedInfo fields; all other OrderTypes map TRUE_CARD_* fields and use parameter-driven values.

⚠ Guard: If CustomerTypeInfo.Type == 0 (or null), the rule throws a DATA_ISSUE exception immediately. This prevents CRM calls with unknown customer types.
⚠ RefId: Uses String.valueOfLong(System.nanoTime()) — not the subscriber RefId. This is a random nano-time string used as the JMS correlation key with CRM. The response is matched by RequestCount, not by RefId/ReferenceId.

§18 — Full Source Code (Key Logic)
rule Rules.OMConsumers.OMXFM.Request.Request_CRM_CREATE_UPDATE_SR {
  // @author CHAYATORN-PC
  then {
    boolean isActResub = (orderCurrentActivity.RequestCount > 0 && orderRequest.IsOrderResubmitted);
    try {
      // POU loop
      // employeeId: saleId if present, else param EMPLOYEE_ID
      // detail: UserText if present, else param DETAIL
      if (orderRequest.OrderData.Customer.CustomerTypeInfo == null
          || orderRequest.OrderData.Customer.CustomerTypeInfo.Type == 0)
        throw Exception.newException("DATA_ISSUE", "CustomerTypeInfo.type not found", null);

      String refId = String.valueOfLong(System.nanoTime());  // NOT subscriber RefId

      Events.OMConsumers.OMXFM.Request.CRM_CREATE_UPDATE_SR reqEvent =
        Event.createEvent("xslt://{{/Events/.../CRM_CREATE_UPDATE_SR}} <!-- §9: OrderType branching CALL_VER_* vs TRUE_CARD_* -->");
      Event.Ext.sendEventImmediate(reqEvent);  // NO assertEvent — fire-and-forget
      isSkipped = false;
      if(!isActResub) { orderCurrentActivity.RequestCount++; }

      // Logger audit (sendEventImmediate)
      // COU loop — same pattern, always uses params for employeeId/detail

      if (!isSkipped) {
        orderCurrentActivity.Status = RuleFunctions.Helpers.GetActivityStatusString("1", false);
        RuleFunctions.Helpers.SendDataToDB(orderRequest);  // no SendFirstRequestEvent
      } else {
        RuleFunctions.Helpers.SkipActivity(orderRequest, orderCurrentActivity, "4");
      }
    } catch(Exception ae) {
      RuleFunctions.Helpers.HandleActivityException(orderRequest, orderCurrentActivity, ae, "");
    }
  }
}
§19 — Response Message Rule

§19.1 Overview

Response_CRM_CREATE_UPDATE_SR is the only response handler among these 4 FMs that still uses the successResponseCount pattern (count of "000" suffix responses). The IntraSeq block was not adopted here — this matches the fire-and-forget request pattern.
