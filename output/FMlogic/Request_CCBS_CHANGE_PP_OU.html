CCBS_CHANGE_PP_OU

FM Logic Documentation — Change Price Plan at OU Level (COU + POU Scopes; Shared Allowance; LargeCustomer LogicalDate; SOC Sequence Pre-allocation; OMXFM external dispatch)
Rule: Rules.OMConsumers.OMXFM.Request.Request_CCBS_CHANGE_PP_OU ActivityID: CCBS_CHANGE_PP_OU Priority: 5 Pattern: Per-OU dispatch (COU first, then POU) Used in step: 17 Generated: 2026-09-11
§1 — Overview & Purpose

CCBS_CHANGE_PP_OU registers a price plan change at the OU (Organizational Unit) level in the OMX FM system. It iterates all ParentOUs; for each POU it first checks ChildOUs (COU scope), then the ParentOU itself (POU scope). If the OU's Agreement has Offers and passes PreExecCheck, it dispatches one CCBS_CHANGE_PP_OU event per qualifying OU. The payload contains the FE price plan offer (ServiceType=80, FE_OR_CCBS=FE), its parameters, related offers, and optionally a shared-allowance CAP SOC entry.

Key design notes:
  • COU before POU: For each ParentOU, ChildOUs are processed first (inner loop), then the ParentOU Agreement is processed (outer). Each qualifying scope gets one dispatch.
  • PurgePendingRequestsBeforeResubmit: Called at start when isActResub is true (unlike some other FMs). Clears any pending/incomplete requests before resubmitting.
  • varPP selection: XSLT selects the FE price plan offer via Offers[ServiceType='80' and ExtendedInfo/Name='FE_OR_CCBS' and ExtendedInfo/Value='FE'][1]. Only this offer's data drives the payload.
  • isSharedAllowance + capSoc: If the FE PP offer has SPECIAL_OFFER_INDICATOR=CSH, iterates RelatedOffersArray to find the one whose GetSplOffIndForSoc == "CAP". If found → adds a special ns9:parameterInfoWithSoc with static name="Agreement level offer instance ID".
  • LargeCustomerIndicator=89: Computes tomorrowLogicalDate (+1 day midnight) at the top. Inside XSLT → adds ns6:EnclosedClientInfo/ns6:LogicalDate: uses varPP.EffectiveDate if exists, else tomorrowDate.
  • FUT_TYPE UserText append: If orderRequest.ExtendedInfo[FUT_TYPE] is 'NXTPP' or 'FUTPP' → appends Thai text ';เปลี่ยน PP โดย omx future order;' to UserText.
  • SOC sequence pre-allocation: countOfers + countRelatedOffersArray is sent in ns3:GetSequenceValueRequest.ns3:incrementByCount to pre-allocate SOC sequence numbers (SOC_SEQ_NO).
  • ChargeDistributionDetailsInfo: If varPP.RCIndicator=65 → adds ns8:ChargeDistributionDetailsInfo for the main PP offer and any RelatedOffersArray[RcIndicator=65], pointing to accountId as TargetPayChannelId.
  • Fan-in CRITICAL NOTE: Response RF uses boolean(Response["000"]) — returns "true" if ANY response is "000". This is NOT compared to RequestCount. If COU and POU both dispatch, the activity completes as soon as the FIRST "000" response arrives — the second response may be ignored or processed after completion. See §19.4 for analysis.
  • ReferenceId IS populated in the response concept (from eventResponse.RefID) — unlike OMX_ADD_FUT_OFFERS.

§5 — Execution Flow Diagram
  1. isActResub: RequestCount>0 && IsOrderResubmitted.
  2. PurgePendingRequestsBeforeResubmit: If isActResub → call PurgePendingRequestsBeforeResubmit(orderCurrentActivity).
  3. tomorrowLogicalDate: If CustomerGeneralInfo.LargeCustomerIndicator=89 → compute tomorrow midnight date string using DateTime.addDay(DateTime.now(),1).
  4. COU loop (for each ChildOU): If ChildOU has Agreement with Offers → PreExecCheck via GetXMLForAgreementInChildOU → if "true": compute counts, agreementNo, activityReason, userText, accountId, isSharedAllowance/capSoc → dispatch CCBS_CHANGE_PP_OU event (COU variant) → RequestCount++ → Logger.
  5. POU loop (for each ParentOU): After COU iteration — if ParentOU has Agreement with Offers → PreExecCheck via GetXMLForAgreement → if "true": same compute steps → dispatch CCBS_CHANGE_PP_OU event (POU variant) → RequestCount++ → Logger.
  6. isSkipped resolution: If any event sent → Status="1" + SendDataToDB. Else → SkipActivity("4").
§6 — isSharedAllowance / capSoc Detection

For each qualifying OU (COU and POU), before dispatching the event, the rule scans Agreement.Offers for shared allowance:

  1. For each AgreementOffer where ServiceType=="80" AND exists(ExtendedInfo[FE_OR_CCBS=FE]): this is the FE price plan offer.
  2. If exists(ExtendedInfo[SPECIAL_OFFER_INDICATOR=CSH]): iterate its RelatedOffersArray.
  3. For each RelatedOffers entry: call GetSplOffIndForSoc(orderRequest, currRelSoc.Soc).
  4. If result == "CAP" → set capSoc = currRelSoc.Soc and isSharedAllowance = true.

When isSharedAllowance==true, the XSLT adds an extra ns9:parameterInfoWithSoc with static values:

<ns9:parameterInfoWithSoc>
    <ns9:name>Agreement level offer instance ID</ns9:name>
    <ns9:values>Agreement level offer instance ID</ns9:values>
    <ns9:soc>{$capSoc}</ns9:soc>
</ns9:parameterInfoWithSoc>
§7 — LargeCustomerIndicator=89 & EnclosedClientInfo

At the start of the rule (before any OU loop), if CustomerGeneralInfo.LargeCustomerIndicator=89:

tomorrowLogicalDate = DateTime.format(DateTime.addDay(DateTime.now(),1),"yyyy-MM-dd'T'00:00:00XXX")

This computed string is passed to the XSLT. Inside the payload, when LargeCustomerIndicator=89:

  • Adds ns6:EnclosedClientInfo block with ns6:LogicalDate.
  • xsl:choose: if varPP/EffectiveDate exists → use varPP.EffectiveDate; else → use tib:add-to-dateTime(... (compute tomorrow midnight inline inside the XSLT as well).
The rule computes tomorrowLogicalDate in BE but the XSLT also computes tomorrow inline (using tib:add-to-dateTime). The BE-computed variable is passed to the XSLT as a param but the XSLT uses its own tib:add-to-dateTime in the else branch — so the param tomorrowLogicalDate is declared but only the XSLT-internal computation is actually used for the else branch. This is a minor redundancy.

§18 — Full Source Code (Condensed)
rule Rules.OMConsumers.OMXFM.Request.Request_CCBS_CHANGE_PP_OU {
    attribute { priority = 5; forwardChain = true; }
    declare { OrderRequest orderRequest; Activity orderCurrentActivity; }
    when { /* extId / ActivityID=="CCBS_CHANGE_PP_OU" / NextActivityID / Status=="WAITING" */ }
    then {
        isActResub = (RequestCount>0 && IsOrderResubmitted);
        try {
            if(isActResub) PurgePendingRequestsBeforeResubmit(orderCurrentActivity);
            if(LargeCustomerIndicator==89)
                tomorrowLogicalDate = DateTime.format(DateTime.addDay(now,1),"yyyy-MM-dd'T'00:00:00XXX");

            for(iPou...) {
                // COU loop: ChildOU.Agreement.Offers
                for(iCou...) {
                    if(childOu.Agreement.Offers@length > 0) {
                        chkRes = GetXMLForAgreementInChildOU + XPath.execute(PreExecCheck);
                        if(chkRes=="true") {
                            countOfers = XPath.evalAsInt(count(Agreement.Offers));
                            countRelatedOffersArray = XPath.evalAsInt(count(Agreement/*/RelatedOffersArray));
                            agreementNo = childOu.Agreement.AgreementId;
                            activityReason = XPath ... "CREQ";
                            userText = childOu.Agreement.AgreementActivityInfo.UserText;
                            accountId = tib:if-absent(Account[AgreementId=agreeId]/AccountID, Account[AgreementRefId=refId]/AccountID);
                            // isSharedAllowance detection
                            for(iOUSoc: ServiceType=80 && FE_OR_CCBS=FE) {
                                if(SPECIAL_OFFER_INDICATOR=CSH) {
                                    for(iRelSoc: GetSplOffIndForSoc=="CAP") capSoc=soc; isSharedAllowance=true;
                                }
                            }
                            reqEvent = Event.createEvent("xslt://CCBS_CHANGE_PP_OU [COU variant]"); /* see §9 */
                            Event.Ext.sendEventImmediate(reqEvent); RequestCount++; isSkipped=false;
                            Logger("Request Sent for CCBS_CHANGE_PP_OU");
                        }
                    }
                }
                // POU loop: ParentOU.Agreement.Offers
                if(parentOu.Agreement.Offers@length > 0) {
                    chkRes = GetXMLForAgreement + XPath.execute(PreExecCheck);
                    if(chkRes=="true") {
                        // same compute + isSharedAllowance detection for parentOu
                        reqEvent = Event.createEvent("xslt://CCBS_CHANGE_PP_OU [POU variant]"); /* see §9 */
                        Event.Ext.sendEventImmediate(reqEvent); RequestCount++; isSkipped=false;
                        Logger("Request Sent for CCBS_CHANGE_PP_OU");
                    }
                }
            }
            if(!isSkipped) { Status="1"; SendDataToDB(orderRequest); }
            else { SkipActivity("4"); }
        } catch(ae) { HandleActivityException; }
    }
}
§19 — Response Message Rule (Response_CCBS_CHANGE_PP_OU)

§19.1 — Overview

Handles incoming responses from the CCBS FM Price Plan change. Creates a ResponseBase concept (with ReferenceId mapped from RefID), appends to currActivity.Response, sends Logger audit, and checks if ANY "000" response exists — not compared to RequestCount. Returns "true" as soon as any success response arrives.

§19.4 — Response Completion Logic

AttributeValue
Success XPathboolean($currActivity/Response[tib:right(tib:trim(ResponseCode), 3) = "000"])
Fan-in conditionANY response with "000" suffix → return "true"
RequestCount comparisonNone — does NOT check RequestCount
[HIGH] Fan-in design defect: The response function returns "true" as soon as ANY response has a "000" code, regardless of how many events were dispatched (RequestCount). If both COU and POU OUs were each dispatched (RequestCount=2), the activity is marked complete as soon as the first "000" response arrives — the second response may arrive after the ProcessFlow has already advanced, causing it to be lost or handled incorrectly. This contrasts with the standard fan-in pattern used in most other FMs (count("000") == RequestCount). Mitigation: if in production only one scope ever qualifies per activity run, this may never cause issues — but this is architecturally fragile. Should be investigated during migration.
