Request_INTX_GET_SIM_INFO_BY_SIM

Per-subscriber multi-SIM parallel INTX lookup by ICCID — writes SIM_STATUS, SIM_TYPE, SIM_COMPANY, SIM_PAIR_MSISDN, IMSI, SIM_DEALER to ResourceInfo; BULKESIM and BATCH special modes
Target: INTX (GetSIMInfoByICCID) Pattern: Multi-SIM per-subscriber fan-out forwardChain: true Author: awalia-t420 Generated: 2026-08-04
§1 Overview & Purpose

Queries the INTX backend (GetSIMInfoByICCID) for each subscriber's SIM card information. Unlike other INTX FMs, each subscriber may generate multiple requests — one for the primary SIM and additional ones for multi-SIM (MSIM) cards from either a MSIM_TO_CANCEL cancel-list or from TR_MULTISIM_IND=RES offers. The response writes SIM attributes back to the subscriber as ResourceInfo concept instances. Two special modes are activated by activity parameters: BULKESIM adds ICC_ID and VENDOR ExtendedInfo, and BATCH sets SubscriberId/SubscriberType from the response.

Non-standard request count: Each subscriber may generate 1+N requests (primary SIM + MSIM count). Fan-in is still by total RequestCount, so the count accumulates across all SIM events from all subscribers.
[DEAD CODE]: PurgePendingRequestsBeforeResubmit and IntraActivitySequencing.ActionRequestEvent calls are commented out. PurgePendingRequestsBeforeResubmit not executed on resubmit for this FM.
Custom response concept: Uses Concepts.FM.Response.INT_GetSIMInfoRes (not ResponseBase). Fields include SearchKey, SimType, SimStatus, SimCompany, etc. The extId is generated in BE code and passed as XSLT param (not generated inside XSLT as in ResponseBase pattern).
isASRMCompanyCode gate: String.length(res.SimStatus) > rmStatusLength (global variable). ALL ResourceInfo write-backs are gated on this boolean — if INTX returns a short status code the write-backs do not execute.

§6 Multi-SIM Fan-out Logic

After the primary reqEvent is sent (Tier A), one of two additional tiers fires depending on subscriber ExtendedInfo content:

Tier A — Primary SIM (always)

  • Source: subscriber.ResourceInfo[ResourceName="SIM"].ValuesArray → currSIM
  • Event: reqEvent with XSLT param $currSIM → ns:iccid
  • RequestCount++; AllowWriteLog audit

Tier B — MSIM_TO_CANCEL list (if present)

  • Condition: exists(subscriber/ExtendedInfo[Name="MSIM_TO_CANCEL"])
  • Value: subscriber/ExtendedInfo[Name="MSIM_TO_CANCEL"]/Value
  • Parse: String.split(msimToCancelString, "\\|")
  • Loop: for each simValue in list → send reqEvent2 with $simValue → ns:iccid
  • RequestCount++ per item; AllowWriteLog audit per item

Tier C — TR_MULTISIM_IND Offers (if MSIM_TO_CANCEL absent)

  • Scan: SubscriberOffers[] looking for ExtendedInfo[Name="TR_MULTISIM_IND" and Value="RES"] AND ParameterInfo[ParamName="Related SIM"]/ValuesArray
  • Value: curoffer/ParameterInfo[ParamName="Related SIM"]/ValuesArray[1]
  • For each qualifying offer → send reqEvent2 with $simValue
  • RequestCount++ per offer; AllowWriteLog audit per offer
Fan-in caveat: RequestCount accumulates ALL events (Tier A + B/C) across ALL subscribers. The "000" fan-in check must match the total. This means a single subscriber with 3 MSIMs adds 4 to RequestCount.

§10 Custom Response Concept — INT_GetSIMInfoRes

Unlike most FMs that use Concepts.FM.Base.ResponseBase, this FM creates a custom Concepts.FM.Response.INT_GetSIMInfoRes instance. This concept carries both the standard response metadata and the SIM-specific data extracted from INTX.

  • createObject
    • object @extId ← $extId (generated in BE, passed as XSLT param)
      • ResponseCode ← $eventResponse/ResponseCode [xsl:if]
      • ResponseMessage ← $eventResponse/ResponseMsg [xsl:if]
      • CompletionStatus ← $eventResponse/CompletionStatus [xsl:if]
      • ReferenceId ← $eventResponse/RefID [xsl:if]
      • SearchType ← "SERIAL_NO" Hardcoded
      • SearchKey ← ns1:simInfo/ns1:serialNo [xsl:if]
      • SimType ← tib:trim(ns1:simInfo/ns1:simType)
      • SimStatus ← tib:trim(ns1:simInfo/ns1:resourceStatus)
      • SimCompany ← tib:trim(ns1:simInfo/ns1:simCompanyCode)
      • SimPairWithMobile ← tib:trim(ns1:ctnInfo/ns1:ctn)
      • SimImsi ← tib:trim(ns1:simInfo/ns1:imsi)
      • SimDealer ← tib:trim(ns1:simInfo/ns1:dealer)
§11 Response Write-back — ResourceInfo & ExtendedInfo

§11.1 — isASRMCompanyCode Gate

int rmStatusLength = XPath("$globalVariables/OMX_OM/BizRules/RMStatusLength"); boolean isASRMCompanyCode = (String.length(res.SimStatus) > rmStatusLength); // ALL ResourceInfo write-backs require isASRMCompanyCode == true

§11.2 — SIM Correlation

The subscriber is matched to the response by comparing res.SearchKey (ICCID from INTX response) against currSIM (subscriber's SIM ICCID from ResourceInfo). CurrSIM is now read via a direct subscriber.ResourceInfo[r].ValuesArray loop (not XPath — more efficient).

§17 Migration Notes & Recommendations

Functional Requirements

RefRequirement
R1Extract currSIM from subscriber.ResourceInfo[ResourceName="SIM"].ValuesArray; skip subscriber if blank.
R2Skip subscriber if SIM_STATUS already populated AND PROJ != "BULKESIM".
R3Three-tier fan-out per subscriber: primary SIM, then MSIM_TO_CANCEL pipe-list, else TR_MULTISIM_IND offers.
R4Payload: ns:GetSIMInfoByICCIDReq with ns:correlatedId=OMXTrackingId and ns:iccid=ICCID.
R5Credential gate on IsEnableUserPass='true'.
R6Audit gated by AllowWriteLog(OrderType) — both request (per event) and response.
R7Response: use custom INT_GetSIMInfoRes concept; extId generated in BE and passed as XSLT param.
R8Match response to subscriber by res.SearchKey == currSIM. All write-backs gated on isASRMCompanyCode = length(SimStatus) > rmStatusLength.
R9MSIM ResourceInfo names/extIds get _<SearchKey> suffix when res.SearchKey != currSIM.
R10BULKESIM mode: write ICC_ID and VENDOR ExtendedInfo.
R11BATCH mode: write dummyMsisdn→SubscriberId, simCompanyCode→SubscriberType, itemId→simItemId ExtendedInfo.
R12Fan-in: standard "000" count == RequestCount (total across all SIM events, all subscribers).

Design Risks

RiskSeverityMitigation
RequestCount accumulates ALL SIM events including MSIM — fan-in math can be surprising if MSIM counts vary per subscriber MEDIUM Ensure MSIM_TO_CANCEL and TR_MULTISIM_IND are stable during the FM window; document the variable-count pattern
PurgePendingRequestsBeforeResubmit commented out — resubmit may produce duplicate RequestCounts MEDIUM Verify resubmit behavior for multi-SIM scenario; re-enable or ensure reqSuccess dedup covers all cases
IMSI write-back in COU branch lacks the SearchKey==currSIM guard that POU branch has LOW Verify COU IMSI write-back is correct for MSIM responses; may write MSIM IMSI to wrong subscriber
