Request_CCBS_UPD_CREDIT_CLASS

CCBS Credit Class Update — fire-and-forget pattern with complex multi-source credit class priority chain
Backend: CCBS Author: awalia-t420 Priority: 5 Pattern: FIRE-AND-FORGET (no IntraActivitySequencing) Fan-in: IsAllResponseSuccess
§1 — Overview & Purpose
CRITICAL ARCHITECTURE DIFFERENCE — Fire-and-Forget: This FM does NOT use IntraActivitySequencing.ActionRequestEvent or Event.assertEvent. Instead it calls Event.Ext.sendEventImmediate(reqEvent) directly and manually increments orderCurrentActivity.RequestCount++. Fan-in uses IsAllResponseSuccess(currActivity) rather than IntraActivitySequencing.ActionResponseEvent.
CCBS_UPD_CREDIT_CLASS updates the credit class on each CCBS Account. The credit class value comes from a complex 5-source priority chain: CVSS result, ODS result, existing/source credit class, and CCBS default — gated by account type, customer type, and exclusion lists.
5-way credit class priority (L9CreditClass): carrySource (OT=8 carry logic) → carryODS (ODS ExtInfo present + active account) → ODS present → CVSS present → CCBS default (no-op, don't send event).
Global exclusion lists: Three global variables gate whether credit class is updated: NoCreditClassChangeCC, NoCreditClassChangeSubType, NoCreditClassChangeTargetCC. If the order's credit class / subtype / target CC is on any list, the event is NOT sent.

§17 — Migration Notes & Recommendations
RiskSeverityMitigation
Fire-and-forget pattern (sendEventImmediate + manual RequestCount++) does NOT go through IntraActivitySequencing. If RequestCount is miscounted (e.g., due to resubmit), fan-in via IsAllResponseSuccess may hang or complete prematurely HIGH In migration, standardize on IntraActivitySequencing or implement explicit request tracking with idempotency
L9CreditClass priority chain has 5 sources; the logic depends on correct ordering of FM19 (CVSS) and FM20 (ODS) completing before FM21 MEDIUM Document FM19→FM20→FM21 dependency chain; validate ProcessConfig activity sequencing enforces it
Three global exclusion lists (NoCreditClassChangeCC, SubType, TargetCC) — if these lists change, behaviour changes silently without code change MEDIUM Externalise exclusion lists to a configuration store with change audit trail
CVSSCreditClass read directly from Account.AccountManagementInfo.CreditClass — this is the value FM19 OVERWROTE. The original value is backed up in CURRENT_CREDITCLASS. This means FM21's "CVSS" source is the post-FM19 value, not the raw CVSS API response MEDIUM Document data flow clearly: FM19 writes CVSS result to Account.CreditClass; FM21 reads it from there
Hardcoded userId=60001 in CCBS request LOW Externalise to configuration in migration
