§1 — Overview & Purpose

Retrieves partial order data from the OMX internal ESB service. This FM is used in the PREPAID_REGISTRATION process (step 3) to recover customer identification details, a prior partial order ID, and multi-level extended info attributes (order, customer, account, subscriber, agreement) that may exist from a partially completed prior order.


The response RF merges the retrieved data into the in-memory OrderRequest concept at multiple levels, enabling downstream activities to work with enriched data even when the originating request was incomplete.

Key trait: Uses subscriber MSISDN as the correlation RefId (not psub.RefId as most other FMs do). This means the response is correlated by phone number rather than a generated tracking ID.

§5 — Execution Flow Diagram
  1. Resubmit check — set isActResub = (RequestCount > 0 && IsOrderResubmitted)
  2. Load activity config — retrieve nextAct by ExtId; read PreExecCheck XPath
  3. Loop ParentOU — for each ParentOU[p], loop each Subscriber[ps]
  4. Skip-check — search Response[] for matching RefId + CompletionStatus==2; if found, skip subscriber
  5. PreExecCheck — if PreExecCheck present, evaluate XPath against subscriber XML; skip if "false"
  6. Build request event — XSLT → GetPartialOrderDataReq; RefId = psub.MSISDN
  7. Send JMS event — Event.Ext.sendEventImmediate(reqEvent)
  8. Increment RequestCount — unless resubmit
  9. Unconditional audit log — Logger event with AUDIT_TRACE "Request Sent for OMX_GET_PARTIAL_ORDER_DATA"
  10. Loop ChildOU — same logic; RefId = csub.MSISDN
  11. Status update — if not skipped: Status = "1" (IN_PROGRESS), persist; else SkipActivity("4")
  12. Exception handler — HandleActivityException(orderRequest, orderCurrentActivity, ae, "")
§6 — Rule Action (THEN) — Logic Detail

Resubmit detection: isActResub = (RequestCount > 0 && IsOrderResubmitted) — if true, RequestCount is not incremented again.

Response completion check: Before sending, scans orderCurrentActivity.Response[] for any entry matching ReferenceId == pSubRefId with CompletionStatus == 2. If found, the subscriber's request is already successful and is skipped.

RefId choice: Unlike most OMXFM rules that use psub.RefId, this rule uses psub.MSISDN as the RefId. This means the JMS correlation is by phone number. ChildOU likewise uses csub.MSISDN.

⚠ Audit Log NOT gated by AllowWriteLog

The audit Logger event fires unconditionally for every subscriber request. Other OMXFM rules gate the audit with RuleFunctions.Helpers.AllowWriteLog(orderRequest.OrderData.OrderType). This FM skips that check, meaning audit logs always write regardless of order type.

§17 — Migration Notes & Recommendations

Functional Requirements

#Requirement
R1Query OMX internal service for partial order data using subscriber MSISDN as the correlation key
R2Populate CustomerName.Identification and IdentificationType only if currently blank
R3Add PARTIAL_ORDER_ID to order-level ExtendedInfo if not already present
R4Merge dynamic extended info arrays at order, customer, account, subscriber, and agreement levels (de-duplicate by Name)
R5Create Agreement concept for ParentOU and ChildOU if null, then populate AgreementExtendedInfo
R6Support resubmit — do not double-increment RequestCount on resubmit

Design Risks

RiskSeverityMitigation
RefId = MSISDN (not generated tracking ID) — if multiple orders share the same MSISDN, response correlation may be ambiguousHIGHIn modernization, use a generated UUID as correlation key; pass MSISDN only in payload
Audit log unconditional — no AllowWriteLog gateMEDIUMAdd AllowWriteLog gate to match other FMs; or document as intentional policy exception
Dynamic extended info merge — de-dup by Name, but all AgreementExtendedInfo entries come from a single response (not per-OU) — all ParentOU/ChildOU Agreements get the same extended infoMEDIUMVerify this is expected behaviour; if not, request must pass OU-specific keys
🐛 BUG — Account ExtendedInfo Loop Infinite Iteration (Response RF line 64)

The inner loop iterates AccountExtendedInfo entries but increments the outer loop variable i instead of the inner loop variable a:

// BUG: inner loop variable `a` never advances; outer `i` increments
for (int a = 0; a < acctExtLen; i++) {   // ← should be a++

This will cause an infinite loop when acctExtLen > 0 and the outer account loop has not exhausted all accounts. The outer i index eventually goes out of bounds for acct, triggering an ArrayIndexOutOfBounds exception. In practice this means Account-level ExtendedInfo is never populated without an error.

Fix: Change i++ to a++ on line 64 of the rulefunction.

§18 — Full Source Code
rule Rules.OMConsumers.OMXFM.Request.Request_OMX_GET_PARTIAL_ORDER_DATA {
  attribute { priority = 5; forwardChain = true; }
  declare {
    Concepts.OrderRequest.OrderRequest orderRequest;
    Concepts.OM.ProcessConfig.Activity orderCurrentActivity;
  }
  when {
    orderCurrentActivity@extId == orderRequest.ProcessFlow.NextActivityName;
    orderCurrentActivity.ActivityID == "OMX_GET_PARTIAL_ORDER_DATA";
    orderRequest.ProcessFlow.NextActivityID == "OMX_GET_PARTIAL_ORDER_DATA";
    orderCurrentActivity.Status == "WAITING";
  }
  then {
    boolean isActResub = (orderCurrentActivity.RequestCount > 0 && orderRequest.IsOrderResubmitted);
    try {
      // ... PreExecCheck + ParentOU/ChildOU subscriber loop ...
      // For each subscriber: build GetPartialOrderDataReq event (§9.8)
      // RefId = psub.MSISDN / csub.MSISDN (NOT psub.RefId)
      // Audit log fires unconditionally (no AllowWriteLog gate)
      if (!isSkipped) {
        orderCurrentActivity.Status = RuleFunctions.Helpers.GetActivityStatusString("1", false);
        RuleFunctions.Helpers.SendDataToDB(orderRequest);
      } else {
        RuleFunctions.Helpers.SkipActivity(orderRequest, orderCurrentActivity, "4");
      }
    } catch (Exception ae) {
      RuleFunctions.Helpers.HandleActivityException(orderRequest, orderCurrentActivity, ae, "");
    }
  }
}
