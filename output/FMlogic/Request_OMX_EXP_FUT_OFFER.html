§1 — Overview & Purpose
OMX_EXP_FUT_OFFER records the expiry of future SOC offers in the OMX FM system. It sends a futureOrderWithSoc message (schema identical to OMX_ADD_FUT_OFFER) using futureType='EXPSOC' to mark existing future SOCs as expiring. It processes four contexts in order: ParentOU Agreement → ParentOU Subscriber → ChildOU Agreement → ChildOU Subscriber. Offers where TR_NEXT_OFFER or TR_NEXT_PP is defined are skipped (the offer is being replaced, not expired).
This rule reuses the same JMS event (OMX_ADD_FUTURE) and schema as OMX_ADD_FUT_OFFER. The operation is differentiated at OMX FM by ns:futureType='EXPSOC' (vs 'FUTSOC' in the ADD rule). The response is also the same event type.

effectiveDate Resolution — Three-way priority (Subscriber variants)

// Priority order in XSLT:
1. if MCS_EXP_DATE_VALUE present // MCS-driven expiry date overrides all
    → ns:effectiveDate = MCS_EXP_DATE_VALUE
2. else if LOGICALDATE_PROV = 'B' OR DataInfo/ExpDate present
    → ns:effectiveDate = futOrderDate  // = expDate (used to be expDate+1 day)
3. else
    → ns:effectiveDate = EXP_DATE_VALUE  // direct expiry date

// Agreement variants: only 2 branches (no LOGICALDATE_PROV/DataInfo check)
1. if MCS_EXP_DATE_VALUE → use it
2. else → EXP_DATE_VALUE if present

§17 — Migration Notes, Bugs & Recommendations
Bug #1 — ChildOU MCS_EXP_DATE_VALUE effectiveDate typo (line ~353 XSLT):
The xsl:when test checks for MCS_EXP_DATE_VALUE but the xsl:value-of reads from MCS_EXP_DATE_VALU (missing trailing 'E'). Result: for ChildOU Subscriber offers that have MCS_EXP_DATE_VALUE, the ns:effectiveDate will be blank. Falls through to the LOGICALDATE_PROV/EXP_DATE_VALUE fallback.
Bug #2 — TR_NEXT_OFFER / TR_NEXT_PP skip check absent for ChildOU:
ParentOU Agreement skips offers where TR_NEXT_OFFER is non-blank. ParentOU Subscriber skips offers where TR_NEXT_OFFER or TR_NEXT_PP is non-blank. ChildOU Agreement and ChildOU Subscriber loops do NOT perform this check — offers with next-offer replacements will still receive EXP_FUT_OFFER processing.
Dead variable — logicalDate (lines 26–31):
DateTime logicalDate = DateTime.parseString(logicalDateRes.LogicalDate, ...) is parsed but requestedDate = DateTime.now() is set separately and is what gets sent. logicalDate is never used.
futOrderDate = expDate (not +1 day):
Line 185 shows // DateTime futOrderDate = DateTime.addDay(expDate, 1); commented out. The current code uses futOrderDate = expDate — the expiry is on the same day as the offer's expiry date. This was intentionally changed from the original design; preserve this behavior.
RELATED_ORDER forwarded in Agreement variants only:
RELATED_ORDER ExtendedInfo is forwarded via xsl:for-each in Agreement variants (①③) but not in Subscriber variants (②④). This appears intentional but should be verified.
