# Request_OMX_SUBMIT_POSTPAID_ADD_BENEFIT

> Submits a child order to the OMX SubmitOrder service per subscriber, carrying loyalty-filtered offers (TR_SPECIAL_OFFER_IND=LY). ORDER_TYPE driven by activity parameter.

**Backend:** OMX SubmitOrder (Child Order) | **Fan-out:** POU + COU subscribers | **Event:** OMX_CREATE_CHILD_ORDER | **Author:** DESKTOP-995HR2V | **Lines:** 134 | **Step:** 83 | **forwardChain:** true

---

## §1 — Overview & Purpose

Submits a child order to the OMX SubmitOrder service for each subscriber, carrying loyalty offers (filtered by `TR_SPECIAL_OFFER_IND=LY`). Unlike FM calls that target external backends, this FM creates an **internal OMX child order** using the `OMX_CREATE_CHILD_ORDER` event. The ORDER_TYPE and SBM channel are configurable via activity parameter and global variable. A monotonic `childIndex` counter is used to construct unique child order IDs across POU and COU subscribers.

| Attribute | Value | Notes |
|-----------|-------|-------|
| Backend event | `Events.OMConsumers.OMXFM.Request.OMX_CREATE_CHILD_ORDER` | Internal OMX child order submission |
| Schema NS (ns) | `http://services.omx.truecorp.co.th/SubmitOrder` | SubmitOrder service payload |
| Payload root | `ns:submitOrderRequest` | |
| Fan-out | POU direct subscribers first, then COU subscribers | POU→Sub, then POU→COU→Sub |
| RefID | Subscriber RefId (bare) | Always emitted |
| childIndex | Monotonic counter across ALL subscribers (POU+COU combined) | Starts at 0; increments before resub check |
| orderId | `concat(OrderID, "-", childIndex)` | Unique child order ID per subscriber |
| ORDER_TYPE | From activity parameter `ORDER_TYPE` | Emitted as `ns:orderType` |
| channel | `concat(Channel, "-OMX")` | Appends "-OMX" suffix |
| SBM_CHANNEL | `globalVariables/OMX_OM/BizRules/Loyalty/SBMChannel` | From global variable |
| Primary offer filter | FE_OR_CCBS="FE" AND SocProperties contains "TR_SPECIAL_OFFER_IND=LY" | Loyalty FE offers |
| Secondary offer block | Gated by existence of CCBS loyalty offers; sends FE ServiceType=86 paid offers | See §9 |
| PurgePendingRequestsBeforeResubmit | ABSENT | Not called on resubmit |
| Response concept | `Concepts.FM.Response.OMX_CreateChildOrder` | Dedicated; captures childOmxTrackingId |
| Fan-in | RequestCount == successResponseCount (suffix "000") | Standard count-match |

> **[MEDIUM]** `childIndex++` happens *before* the resub guard check. On resubmit, already-completed subscribers are skipped but their `childIndex` still increments. The `orderId` suffix for re-sent subscribers may differ from the original run.

> **[MEDIUM]** `PurgePendingRequestsBeforeResubmit` is absent. If the original child order is still pending when resubmit fires, duplicate child orders may be created.

> **[INFO]** This FM creates an internal OMX child order — not a direct call to a backend system like CCBS or NAS. The child order is then processed independently by the OMX child order engine.

## §5 — Execution Flow

1. **Init:** `isActResub` = (RequestCount > 0 && IsOrderResubmitted). Read `param` (ORDER_TYPE). `chkXPath` = nextAct.PreExecCheck. `isSkipped = true`. `childIndex = 0`.
2. **POU subscriber loop** (POU p → Sub ps): `childIndex++` (first, before resub guard). Resub guard: skip if Response[ReferenceId==pSubRefId && CompletionStatus==2]. PreExecCheck. Send `OMX_CREATE_CHILD_ORDER` event. RequestCount++ if !isActResub. isSkipped = false.
3. **COU subscriber loop** (POU p → COU c → Sub cs): same — `childIndex++` first. Resub guard + PreExecCheck + send event + Logger. `childIndex` continues from where POU left off.
4. **Completion:** if (!isSkipped) → Status = GetActivityStatusString("1", false); SendDataToDB. Else → SkipActivity("4").
5. **Exception:** catch(Exception ae) → HandleActivityException(orderRequest, orderCurrentActivity, ae, "")

## §9 — Detailed Payload Build

### §9.1 Activity Parameter

| Parameter Key | Variable | Effect |
|---------------|----------|--------|
| ORDER_TYPE | `param` | Emitted as `ns:orderType` — determines the type of child order |

### §9.2 childIndex & orderId

`childIndex` starts at 0, increments BEFORE the resub guard check. The child order ID is:

```text
ns:orderId = concat(OrderID, "-", childIndex)
```

Example: main order `ORD-123` → child orders `ORD-123-1`, `ORD-123-2`, etc.

### §9.3 Offer Filtering Logic (per subscriber)

| Block | Condition | Offers Included |
|-------|-----------|-----------------|
| Primary (always) | `FE_OR_CCBS="FE" AND SocProperties contains "TR_SPECIAL_OFFER_IND=LY"` | FE loyalty offers — expirationDate, offerName, serviceType, soc |
| Secondary (gated) | `exists(SubscriberOffers[FE_OR_CCBS="CCBS" AND SocProperties contains "TR_SPECIAL_OFFER_IND=LY"])` → then loop FE ServiceType=86 & OfferRate>0 | FE paid data offers when CCBS loyalty offers exist; expirationDate only when RevenueType="OC" |

## §17 — Migration Notes & Recommendations

### Functional Requirements

| Ref | Requirement |
|-----|-------------|
| R1 | Fan-out: POU direct subscribers first, then COU. One child order per subscriber. |
| R2 | childIndex = monotonic counter starting at 0, shared across POU and COU. Increments before resub guard. |
| R3 | orderId = concat(OrderID, "-", childIndex). Unique child order ID per subscriber per original run. |
| R4 | orderType = activity parameter ORDER_TYPE. |
| R5 | channel = concat(Channel, "-OMX"). Always appends "-OMX" suffix. |
| R6 | ExtendedInfo MAIN_TRACKING_ID = OMXTrackingId. ExtendedInfo SBM_CHANNEL = globalVars/Loyalty/SBMChannel. |
| R7 | Primary offers: FE_OR_CCBS="FE" AND SocProperties contains "TR_SPECIAL_OFFER_IND=LY". |
| R8 | Secondary offers: only emitted when exists(CCBS loyalty offers); selects FE ServiceType=86 with OfferRate>0. expirationDate only when RevenueType="OC". |
| R9 | Fan-in: RequestCount == successResponseCount (suffix "000"). |
| R10 | Response captures childOmxTrackingId from submitOrderResponse payload. |

### Design Risks

| Risk | Severity | Mitigation |
|------|----------|-----------|
| childIndex increments before resub guard — orderId suffix may differ on resubmit vs original | [MEDIUM] | Evaluate if downstream SubmitOrder requires idempotent orderId; consider using subscriber RefId in orderId instead of sequential counter |
| PurgePendingRequestsBeforeResubmit absent — risk of duplicate child orders on resubmit | [MEDIUM] | Add PurgePendingRequestsBeforeResubmit if the SubmitOrder service is not idempotent |
| Secondary offer block: CCBS gating and FE ServiceType=86 selection is opaque — business intent unclear | [LOW] | Document the business rule: when is ServiceType=86 a loyalty benefit that needs the child order? |
| SBMChannel from global variable — may differ across environments | [LOW] | Verify SBMChannel value in each target environment; add to deployment checklist |

## §19 — Response Message Rule (Response_OMX_SUBMIT_POSTPAID_ADD_BENEFIT)

### §19.1 Overview

Uses the dedicated `Concepts.FM.Response.OMX_CreateChildOrder` concept (not ResponseBase). Captures an additional `childOmxTrackingId` field from the SubmitOrder response payload — allowing the main order to track the child order tracking ID for downstream correlation.

### §19.2 Scope Variables

| Variable | Type | Role |
|----------|------|------|
| orderRequest | Concepts.OrderRequest.OrderRequest | Order context |
| eventResponse | Events.OMConsumers.OMXFM.Response.OMX_CREATE_CHILD_ORDER | OMX child order response event |
| currActivity | Concepts.OM.ProcessConfig.Activity | Activity state & response list |

### §19.3 OMX_CreateChildOrder Concept Construction

```text
createObject
└── object (OMX_CreateChildOrder)
    ├── @extId              ← OMXUtils:generateTrackingID()                                    [Always]
    ├── ResponseCode        ← $eventResponse/ResponseCode                                      [Conditional]
    ├── ResponseMessage     ← $eventResponse/ResponseMsg                                       [Conditional]
    ├── CompletionStatus    ← $eventResponse/CompletionStatus                                  [Conditional]
    ├── ReferenceId         ← $eventResponse/RefID                                             [Conditional]
    └── childOmxTrackingId  ← $eventResponse/payload/ns:submitOrderResponse/ns:OMXTrackingId   [Conditional — unique to this FM]
```

### §19.4 Fan-in Completion Logic

| Field | Value |
|-------|-------|
| Success XPath | `count($currActivity/Response[tib:right(tib:trim(ResponseCode), 3) = "000"])` |
| Fan-in condition | `currActivity.RequestCount == successResponseCount` |
| Return "true" | All child order submissions completed with ResponseCode suffix "000" |
| childOmxTrackingId | Captured per-response for downstream child order correlation |
